# Архитектура каскадного LLM-классификатора ТН ВЭД ЕАЭС

## 1. Структура каскада

Каскад — это последовательный спуск по 5 уровням дерева ТН ВЭД. На каждом уровне — отдельный вызов LLM со своим контекстом, промптом и валидацией.

```
Уровень 0 ─ Обогащение описания товара
     │
Уровень 1 ─ Раздел (I–XXI)
     │
Уровень 2 ─ Группа (2 цифры: 01–97)
     │
Уровень 3 ─ Позиция (4 цифры)
     │
Уровень 4 ─ Субпозиция (6 цифр)
     │
Уровень 5 ─ Подсубпозиция (8 и 10 цифр)
     │
Валидация ─ Проверка + перекрёстная сверка
```

---

## 2. Уровень 0 — Обогащение описания товара

### Задача
Превратить пользовательский ввод (часто неполный, на сленге, с торговыми марками) в структурированную «карточку товара», пригодную для классификации.

### Что подаётся в LLM
- Сырое описание товара от пользователя
- Чеклист обязательных полей (см. ниже)
- Инструкция: «Заполни карточку. Если информации недостаточно — сформулируй уточняющие вопросы.»

### Выходная структура — «Карточка товара»

```json
{
  "original_description": "...",
  "normalized_description": "...",
  "material": "...",
  "material_composition_pct": { "хлопок": 80, "полиэстер": 20 },
  "function": "...",
  "processing_degree": "сырьё | полуфабрикат | готовое изделие",
  "physical_state": "твёрдое | жидкое | газообразное | порошок | ...",
  "dimensions": "...",
  "weight": "...",
  "packaging": "...",
  "is_set": true/false,
  "is_disassembled": true/false,
  "has_electric_motor": true/false,
  "power_source": "электричество | бензин | ручной | ...",
  "intended_use": "бытовой | промышленный | медицинский | ...",
  "missing_info": ["процент содержания жира", "..."],
  "clarifying_questions": ["Какой процент жира в продукте?", "..."]
}
```

### Элементы контекста
| Элемент | Нужен? | Источник |
|---------|--------|----------|
| Дерево ТН ВЭД | ❌ | — |
| Примечания | ❌ | — |
| Пояснения | ❌ | — |
| ОПИ | ❌ | — |
| Прецеденты | ❌ | — |

### Модель
Тир light (MODEL_LIGHT) — задача несложная, нужна скорость.

## 3. Уровень 1 — Определение Раздела (I–XXI)

### Задача
Из 21 раздела выбрать 1–2 наиболее вероятных, проверить исключающие примечания, вернуть финальный раздел.

### Что подаётся в LLM
- Карточка товара (с Уровня 0)
- Список 21 раздела с полными наименованиями
- Примечания к разделам (особенно исключающие)
- Инструкция по применению ОПИ Правило 1

### Элементы контекста
| Элемент | Нужен? | Что именно | Объём |
|---------|--------|------------|-------|
| Дерево ТН ВЭД | ✅ | Только 21 раздел с наименованиями | Маленький (~1 KB) |
| Примечания к разделам | ✅ | Все примечания ко всем 21 разделам | Средний (~15–20 KB) |
| Примечания к группам | ❌ | Пока не нужны | — |
| Пояснения | ❌ | Слишком детально для этого уровня | — |
| ОПИ | ✅ | Правило 1 (тексты позиций + примечания имеют юридическую силу) | Маленький (~0.5 KB) |
| Прецеденты | ❌ | Не нужны на этом уровне | — |

### Выходная структура

```json
{
  "candidates": [
    {
      "section": "XVI",
      "section_name": "Машины, оборудование и механизмы...",
      "reasoning": "Товар содержит электродвигатель, что указывает на Раздел XVI",
      "exclusion_check": "Примечание 1е к Разделу XVI не исключает данный товар",
      "confidence": 0.85
    }
  ],
  "selected_section": "XVI",
  "applied_rules": ["ОПИ 1"],
  "backtrack_trigger": null
}
```

### Механизм backtracking
Если на Уровне 2 или 3 обнаружится исключение, система возвращается сюда с пометкой «Раздел XVI исключён по примечанию X к группе Y, причина: ...» — и LLM выбирает другой раздел.

### Модель
Тир light (MODEL_LIGHT) — выбор из 21 варианта обычно очевиден.

## 4. Уровень 2 — Определение Группы (2 цифры)

### Задача
Внутри выбранного раздела определить группу. Проверить примечания к группам на исключения.

### Что подаётся в LLM
- Карточка товара
- Выбранный раздел + reasoning с Уровня 1
- Список групп только внутри этого раздела (обычно 5–15 групп)
- Примечания к выбранному разделу (повторно, для контекста)
- Примечания к каждой группе-кандидату внутри раздела
- ОПИ Правило 1

### Элементы контекста
| Элемент | Нужен? | Что именно | Объём |
|---------|--------|------------|-------|
| Дерево ТН ВЭД | ✅ | Группы выбранного раздела с наименованиями | Маленький (~1–3 KB) |
| Примечания к разделу | ✅ | Примечания к выбранному разделу | Маленький (~2–5 KB) |
| Примечания к группам | ✅ | Примечания ко всем группам этого раздела | Средний (~10–30 KB) |
| Пояснения к группам | ⚠️ Опционально | Общие пояснения к группам (вводная часть, без детализации по позициям) | Средний |
| ОПИ | ✅ | Правило 1 | Маленький |
| Прецеденты | ❌ | Пока рано | — |

### Выходная структура

```json
{
  "section": "XVI",
  "candidates": [
    {
      "group": "84",
      "group_name": "Реакторы ядерные, котлы, оборудование и механические устройства...",
      "reasoning": "...",
      "exclusion_check": "Примечание 1 к группе 84 не исключает данный товар"
    },
    {
      "group": "85",
      "group_name": "Электрические машины и оборудование...",
      "reasoning": "...",
      "exclusion_check": "..."
    }
  ],
  "selected_group": "85",
  "applied_rules": ["ОПИ 1"],
  "backtrack_trigger": null
}
```

### Ключевой риск
Примечание к группе может отсылать товар в другой раздел. Например: «В данную группу не включаются изделия, классифицируемые в группе 90». Если такое обнаружено → backtrack.

### Модель
Тир medium (MODEL_MEDIUM) — некоторые разделы (XVI, XI) имеют сложные примечания.

## 5. Уровень 3 — Определение Позиции (4 цифры)

### Задача
Самый сложный уровень. Внутри группы — 10–40 позиций. Здесь впервые нужно применять ОПИ 2–5 для неоднозначных случаев.

### Что подаётся в LLM
- Карточка товара
- Цепочка решений (раздел → группа с reasoning)
- Все позиции внутри выбранной группы с полными текстами
- Примечания к группе (полные, включая определения терминов)
- Пояснения к позициям-кандидатам (из векторной БД через RAG)
- ОПИ Правила 1–5 (полный набор)

### Элементы контекста
| Элемент | Нужен? | Что именно | Объём |
|---------|--------|------------|-------|
| Дерево ТН ВЭД | ✅ | Все позиции выбранной группы с полными текстами | Средний (~3–10 KB) |
| Примечания к группе | ✅ | Полные примечания выбранной группы | Средний (~3–10 KB) |
| Пояснения | ✅✅ | Пояснения к 2–5 наиболее вероятным позициям (RAG) | Большой (~10–30 KB) |
| ОПИ | ✅✅ | Правила 1–5 полностью, с инструкцией по последовательному применению | Средний (~3 KB) |
| Прецеденты | ✅ | Примеры декларирования похожих товаров (RAG из базы прецедентов) | Средний (~5–10 KB) |

### Двухшаговая стратегия для этого уровня

**Шаг 3а — Сужение кандидатов:**
LLM получает список всех позиций группы и выбирает 2–5 наиболее вероятных.

**Шаг 3б — Глубокий анализ кандидатов:**
Для каждого кандидата подгружаются полные пояснения. LLM последовательно применяет ОПИ:
1. Правило 1 → проверка текстов позиций
2. Правило 2а → незавершённые/разобранные изделия
3. Правило 2б → смеси/составные
4. Правило 3а → конкретность описания
5. Правило 3б → основной характер
6. Правило 3в → последняя подходящая позиция

### Выходная структура

```json
{
  "section": "XVI",
  "group": "85",
  "candidates": [
    {
      "position": "8509",
      "position_text": "Машины электромеханические бытовые со встроенным электродвигателем...",
      "reasoning": "...",
      "opi_applied": "ОПИ 1 — текст позиции 8509 конкретно описывает товар",
      "confidence": 0.80
    },
    {
      "position": "8516",
      "position_text": "...",
      "reasoning": "...",
      "opi_applied": "ОПИ 3а — позиция 8509 даёт более конкретное описание",
      "confidence": 0.15
    }
  ],
  "selected_position": "8509",
  "applied_rules": ["ОПИ 1", "ОПИ 3а"],
  "precedents_found": ["Предварительное решение ФТС №... по аналогичному товару: 8509"],
  "backtrack_trigger": null
}
```

### Модель
Тир heavy (MODEL_HEAVY) — здесь нужно качественное рассуждение.

## 6. Уровень 4 — Определение Субпозиции (6 цифр)

### Задача
Внутри позиции выбрать субпозицию. Обычно 2–10 вариантов. Применяется ОПИ Правило 6.

### Что подаётся в LLM
- Карточка товара
- Цепочка решений (раздел → группа → позиция)
- Субпозиции внутри выбранной позиции
- Пояснения к субпозициям (если есть)
- ОПИ Правило 6
- Прецеденты (RAG)

### Элементы контекста
| Элемент | Нужен? | Что именно | Объём |
|---------|--------|------------|-------|
| Дерево ТН ВЭД | ✅ | Субпозиции выбранной позиции | Маленький (~1–3 KB) |
| Примечания к субпозициям | ✅ | Если есть (не у всех групп) | Маленький |
| Пояснения к субпозициям | ✅ | Пояснения с конкретными примерами | Средний (~5–15 KB) |
| ОПИ | ✅ | Правило 6 (субпозиции одного уровня сравниваются только между собой) | Маленький |
| Прецеденты | ✅ | Примеры декларирования на уровне 6 знаков | Средний |

### Выходная структура

```json
{
  "position": "8509",
  "candidates": [...],
  "selected_subposition": "8509 80",
  "applied_rules": ["ОПИ 6", "ОПИ 1"],
  "confidence": 0.85
}
```

### Модель
Тир medium (MODEL_MEDIUM) — выбор обычно более узкий, но нужна точность.

---

## 7. Уровень 5 — Определение Подсубпозиции (8 и 10 цифр)

### Задача
Финальная детализация на уровне ЕАЭС (8 знаков) и национальном уровне (10 знаков). Часто определяется конкретными техническими параметрами.

### Что подаётся в LLM
- Карточка товара (здесь критичны точные технические параметры)
- Цепочка решений
- Подсубпозиции выбранной субпозиции
- Технические критерии (процент содержания, мощность, размер, вес...)

### Элементы контекста
| Элемент | Нужен? | Что именно | Объём |
|---------|--------|------------|-------|
| Дерево ТН ВЭД | ✅ | 8- и 10-значные коды субпозиции | Маленький (~0.5–2 KB) |
| Технические пороги | ✅✅ | «Более 6% жира», «мощностью не более 1 кВт» и т.д. — извлечённые из текстов кодов | Маленький |
| Пояснения | ⚠️ | Редко есть на этом уровне | — |
| Прецеденты | ✅ | На уровне полного 10-значного кода | Средний |

### Критически важно
Если карточка товара не содержит параметра, от которого зависит выбор кода (например, «содержание молочного жира»), система **ДОЛЖНА ОСТАНОВИТЬСЯ** и запросить у пользователя, а не угадывать.

### Выходная структура

```json
{
  "subposition": "8509 80",
  "selected_code_8": "8509 80 00",
  "selected_code_10": "8509 80 000 0",
  "reasoning": "...",
  "confidence": 0.90,
  "missing_parameters": [],
  "final_code": "8509 80 000 0"
}
```

### Модель
Тир light (MODEL_LIGHT) — если параметры известны, выбор обычно однозначный. Если нет — всё равно нужно остановиться.

## 8. Валидация и пост-обработка

### Проверки (программные, без LLM)
1. **Существование кода** — проверка в БД, что 10-значный код реально существует в актуальной номенклатуре
2. **Целостность цепочки** — код 10 → 8 → 6 → 4 → 2 → раздел — все вложения корректны
3. **Ставки и меры** — подтянуть из БД пошлины, НДС, акцизы, нетарифные меры

### Перекрёстная проверка (RAG + LLM)
4. **Сверка с прецедентами** — поиск в базе деклараций/решений по аналогичным товарам
5. **Анализ расхождений** — если прецеденты дают другой код, LLM анализирует причину

### Выходная структура

```json
{
  "final_code": "8509 80 000 0",
  "code_description": "Машины электромеханические бытовые...",
  "duty_rate": "7.5%",
  "vat_rate": "20%",
  "non_tariff_measures": [...],
  "classification_chain": {
    "section": { "code": "XVI", "name": "...", "reasoning": "..." },
    "group": { "code": "85", "name": "...", "reasoning": "..." },
    "position": { "code": "8509", "name": "...", "reasoning": "..." },
    "subposition": { "code": "8509 80", "name": "...", "reasoning": "..." },
    "code_10": { "code": "8509 80 000 0", "name": "...", "reasoning": "..." }
  },
  "opi_applied": ["ОПИ 1", "ОПИ 3а", "ОПИ 6"],
  "confidence": 0.85,
  "risk_flags": [],
  "precedent_match": true,
  "precedent_codes": ["8509 80 000 0"],
  "requires_human_review": false
}
```

## 9. Структура базы данных

### Таблица `tnved_tree` (из Excel tws.by)

Предполагаемая структура Excel от tws.by: код, наименование, ставка ЕТТ. Её нужно обогатить иерархией.

```sql
CREATE TABLE tnved_tree (
    id SERIAL PRIMARY KEY,
    code VARCHAR(10) NOT NULL,          -- '8509800000'
    code_formatted VARCHAR(14),          -- '8509 80 000 0'
    level INTEGER NOT NULL,              -- 1=раздел, 2=группа, 3=позиция, 4=субпозиция, 5=подсубпозиция
    parent_code VARCHAR(10),             -- код родителя
    name_short TEXT,                      -- краткое наименование
    name_full TEXT,                       -- полное наименование с юридическими формулировками
    
    -- Из Excel tws.by:
    duty_rate VARCHAR(100),              -- ставка пошлины (текстовое — бывает составное)
    vat_rate VARCHAR(20),                -- НДС
    excise VARCHAR(100),                 -- акциз
    unit_of_measure VARCHAR(50),         -- единица измерения (кг, шт, л...)
    additional_unit VARCHAR(50),         -- дополнительная единица измерения
    
    -- Служебные:
    section_code VARCHAR(5),             -- римская цифра раздела (для быстрой фильтрации)
    group_code VARCHAR(2),               -- 2-значный код группы
    is_leaf BOOLEAN DEFAULT FALSE,       -- является ли конечным кодом (для декларирования)
    valid_from DATE,
    valid_to DATE,
    updated_at TIMESTAMP
);

-- Индексы для быстрой навигации по каскаду:
CREATE INDEX idx_tnved_parent ON tnved_tree(parent_code);
CREATE INDEX idx_tnved_level ON tnved_tree(level);
CREATE INDEX idx_tnved_section ON tnved_tree(section_code);
CREATE INDEX idx_tnved_group ON tnved_tree(group_code);
CREATE INDEX idx_tnved_code ON tnved_tree(code);
```

### Таблица `tnved_notes` (из PDF ЕЭК — парсинг)

```sql
CREATE TABLE tnved_notes (
    id SERIAL PRIMARY KEY,
    scope_type VARCHAR(10) NOT NULL,     -- 'section' | 'group' | 'subgroup_note'
    scope_code VARCHAR(10) NOT NULL,     -- 'XVI' для раздела, '85' для группы
    note_number VARCHAR(10),             -- '1', '2а', '3' и т.д.
    note_type VARCHAR(20) NOT NULL,      -- 'inclusive' | 'exclusive' | 'definition' | 'general'
    note_text TEXT NOT NULL,             -- полный текст примечания
    references_to TEXT[],                -- ссылки на другие разделы/группы (для исключений)
    
    -- Для RAG:
    embedding_text TEXT,                 -- текст, оптимизированный для эмбеддинга
    
    updated_at TIMESTAMP
);

CREATE INDEX idx_notes_scope ON tnved_notes(scope_type, scope_code);
CREATE INDEX idx_notes_type ON tnved_notes(note_type);
```

### Таблица `tnved_explanatory_notes` (из PDF пояснений ЕЭК)

```sql
CREATE TABLE tnved_explanatory_notes (
    id SERIAL PRIMARY KEY,
    code VARCHAR(10) NOT NULL,           -- код, к которому относится пояснение
    code_level INTEGER NOT NULL,         -- уровень: 2=группа, 4=позиция, 6=субпозиция
    section_type VARCHAR(20),            -- 'general' | 'includes' | 'excludes' | 'examples'
    content TEXT NOT NULL,               -- текст пояснения
    
    -- Для чанкинга и RAG:
    chunk_index INTEGER,                 -- порядковый номер чанка внутри пояснения
    chunk_text TEXT,                     -- текст чанка (для эмбеддинга)
    
    source_file VARCHAR(100),            -- исходный PDF файл
    page_number INTEGER,
    updated_at TIMESTAMP
);

CREATE INDEX idx_expl_code ON tnved_explanatory_notes(code);
CREATE INDEX idx_expl_level ON tnved_explanatory_notes(code_level);
```

### Таблица `tnved_opi` (статическая)

```sql
CREATE TABLE tnved_opi (
    id SERIAL PRIMARY KEY,
    rule_number VARCHAR(5) NOT NULL,     -- '1', '2a', '2b', '3a', '3b', '3c', '4', '5a', '5b', '6'
    rule_text TEXT NOT NULL,             -- полный юридический текст правила
    prompt_instruction TEXT NOT NULL,    -- инструкция для LLM: когда и как применять
    applicable_levels INTEGER[],        -- на каких уровнях каскада применяется [3,4,5]
    priority INTEGER                    -- порядок применения
);
```

### Векторная БД (Qdrant / Pgvector)

```
Collection: explanatory_notes_chunks
  - vector: embedding (1536 / 1024 dim)
  - payload: { code, code_level, section_type, chunk_text, source_file }

Collection: classification_precedents
  - vector: embedding
  - payload: { product_description, assigned_code, source, date, authority }

Collection: court_decisions
  - vector: embedding
  - payload: { case_number, product_description, disputed_codes, final_code, reasoning }
```

## 10. Структуризация Пояснений

### Проблема
Пояснения к ТН ВЭД — это ~97 PDF-файлов (по одному на группу), каждый от 10 до 200+ страниц. Внутри — сплошной текст с определённой, но не машиночитаемой структурой.

### Типичная структура пояснения (внутри PDF)

```
ГРУППА 85
  Общие положения (вводный текст к группе)
  
  85.01 — Электродвигатели и электрогенераторы...
```

### Стратегия парсинга PDF → структурированные данные

**Шаг 1. Извлечение текста**
```bash
# Для каждого PDF пояснений:
pdftotext -layout psn85.pdf psn85.txt
# или через PyMuPDF (fitz) для лучшего сохранения структуры
```

**Шаг 2. Разметка по позициям**
Регулярные выражения для определения границ:
- Заголовок позиции: `^\d{2}\.\d{2}` (например, `85.01`)
- Заголовок субпозиции: может быть обозначен буквами или цифрами внутри позиции
- Ключевые маркеры:
  - `В данную позицию включаются` → section_type = 'includes'
  - `В данную позицию не включаются` → section_type = 'excludes'
  - `В данную субпозицию включаются` → уровень субпозиции

**Шаг 3. Результирующая структура для каждого пояснения**

```json
{
  "group": "85",
  "general_notes": "Общие положения к группе 85...",
  "positions": [
    {
      "code": "8501",
      "title": "Электродвигатели и электрогенераторы...",

          "type": "general",

          "content": "Пояснительный текст..."
        },
        {
          "type": "includes",
          "heading": "В данную позицию включаются:",
          "items": [
            "Двигатели постоянного тока мощностью...",
            "..."
          ]
        },
        {
          "type": "excludes",
          "heading": "В данную позицию не включаются:",
```

**Шаг 4. Чанкинг для векторной БД**
Каждое пояснение к позиции разбивается на чанки:
- Чанк = один смысловой блок (general / includes / excludes / подраздел)
- Размер чанка: 500–1500 токенов
- Перекрытие (overlap): 100–200 токенов
- Метаданные чанка: код позиции, тип секции, номер чанка

## 12. Обработка граничных случаев

### Составные товары / наборы
На Уровне 3 подключается специальный модуль ОПИ 3б:
- LLM получает инструкцию: «Определи, какой компонент придаёт основной характер»
- Входные данные: состав товара из карточки, описание компонентов
- Решение должно быть обосновано (по стоимости, по объёму, по функции)

### Незавершённые / разобранные изделия
На Уровне 3 подключается модуль ОПИ 2а:
- Проверка: «Обладает ли изделие основными характеристиками готового продукта?»
- Если да → классифицируется как готовое

### Товар не найден ни в одной позиции
ОПИ Правило 4 — классификация по аналогии:
- LLM ищет наиболее близкий товар в пояснениях через RAG
- Пониженный confidence → флаг requires_human_review

### Недостаточно данных для выбора
Система ОСТАНАВЛИВАЕТСЯ на **любом уровне** (L0–L5) и возвращает `needs_input`:
```json
{
  "partial_code": "8509 80",
  "determined_to_level": 4,
  "missing_parameters": ["мощность электродвигателя"],
  "question": "Для выбора точного кода необходимо уточнить: мощность электродвигателя",
  "questions": ["Укажите: мощность электродвигателя"],
  "classification_chain_so_far": [...]
}
```

Поле `missing_parameters` поддерживается в схемах уровней L0 (через `missing_info`), L3 (`PositionResult`), L4 (`SubpositionResult`) и L5 (`SubsubpositionResult`). Оркестратор проверяет `state.missing_parameters` **после каждого уровня** и останавливает каскад.

## 12а. Механизм уточнений (needs_input / session resumption)

### Архитектура

```
POST /classify → каскад L0..L5
                    │
          ┌─ completed → ClassifyResponse(status="completed")
          │
          └─ needs_input → сохранить CascadeState в БД
                          → ClassifyResponse(status="needs_input", partial=...)
                                │
                    POST /classify/{session_id}/answer
                                │
                          загрузить CascadeState из БД
                          дополнить product_card ответами
                          перезапустить каскад с stopped_at_level
                                │
                      ┌─ completed → удалить сессию, вернуть результат
                      └─ needs_input → обновить сессию, вернуть partial
```

### Хранение состояния

Таблица `classification_sessions`:
- `session_id` (UUID) — уникальный идентификатор
- `state` (JSONB) — сериализованный `CascadeState` (через `to_dict()`/`from_dict()`)
- TTL: `SESSION_TTL_MINUTES` (по умолчанию 30 минут)
- Лимит итераций: `SESSION_MAX_ANSWERS` (по умолчанию 3)

### Уровни, поддерживающие needs_input

| Уровень | Источник сигнала | Когда срабатывает |
|---------|-----------------|-------------------|
| L0 | `ProductCard.missing_info` + `clarifying_questions` | Недостаточно данных для карточки товара |
| L3 | `PositionResult.missing_parameters` | Неоднозначность между позициями из-за неизвестного параметра |
| L4 | `SubpositionResult.missing_parameters` | Неоднозначность субпозиций |
| L5 | `SubsubpositionResult.missing_parameters` | Технический параметр для финального кода |

### Resume flow

1. Клиент отправляет `POST /classify/{session_id}/answer` с `answers: dict[str, str]`
2. Оркестратор загружает `CascadeState` из БД
3. Ответы мержатся в `product_description` и `product_card`
4. `missing_parameters` и `clarifying_question` очищаются
5. Каскад перезапускается с `stopped_at_level` (не с нуля)
6. При успехе — сессия удаляется из БД
7. При повторном needs_input — сессия обновляется

## 13. Стратегия промптов

### Принципы
1. **Каждый уровень — отдельный системный промпт**, содержащий:
   - Роль: «Ты — эксперт по таможенной классификации»
   - Задачу конкретного уровня
   - Правила (какие ОПИ применять)
   - Формат ответа (JSON-схема)
   - Инструкцию по backtracking

2. **Контекст подаётся в user message**, а не в системном промпте:
   - Карточка товара
   - Релевантные данные из БД (дерево, примечания, пояснения)
   - История решений предыдущих уровней

3. **Chain-of-thought обязателен на Уровнях 3–4**:
   - LLM должен «рассуждать вслух» перед выбором
   - Рассуждение логируется для аудита

### Пример системного промпта для Уровня 3

```
Ты — эксперт по классификации товаров по ТН ВЭД ЕАЭС.

ЗАДАЧА: Определить 4-значную товарную позицию внутри группы {group_code}.

ПРАВИЛА:
1. Применяй ОПИ строго последовательно: Правило 1 → 2а → 2б → 3а → 3б → 3в → 4.
2. Начни с Правила 1: прочитай тексты позиций и примечания.
3. Если товар подходит под несколько позиций — переходи к Правилу 3.
4. Для составных товаров / наборов — используй Правило 3б.
5. Обязательно проверяй пояснения — они содержат примеры.
6. Если обнаружишь, что товар исключён из этой группы — 
   верни backtrack_trigger с указанием причины.

ФОРМАТ ОТВЕТА: JSON (схема ниже).
ОБЯЗАТЕЛЬНО: поле reasoning должно содержать пошаговое рассуждение.
```

```

```

### Имена субпозиций

Имена субпозиций (level 3) включают контекст виртуальных родителей из PDF ЕЭК.
Формат: `"виртуальный_родитель > собственное_имя"`, например: `"миндаль > в скорлупе"`.
Это решает проблему дублирующихся имён (99.6% уникальных vs 82.9% в старом FNS+LCP подходе).
Подробнее: `docs/ett_pdf_migration.md`, `docs/naming_problem.md`.
