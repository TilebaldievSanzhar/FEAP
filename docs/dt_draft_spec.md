# Спецификация модуля «Досье поставки → Проект ДТ»

**Дата:** 2026-07-04
**Статус:** спецификация к реализации (H2 из `docs/product_vision_v2.md`)
**Нормативная база:** Решение КТС № 257 от 20.05.2010 (форма и порядок заполнения ДТ),
Решение КТС № 378 от 20.09.2010 (классификаторы), Решение Коллегии ЕЭК № 75 от
30.05.2023 (структура и формат ДТ, идентификатор R.055).
**Контекст по КР:** `docs/kg_customs_filing_research.md`.

---

## 1. Цель и границы

**Цель.** Из пакета документов поставки и данных компании собрать **проект
Декларации на товары** (все графы декларанта), проверить его тремя слоями
валидаций и выдать в форматах, минимизирующих ручной перенос в АРМ «Брокер».

**Метрика успеха фичи:** время «загрузил инвойс → скачал проект ДТ» < 10 минут;
auto-fill ≥ 75% граф; ≤ 10% автозаполненных значений правится человеком.

**Скоуп v1:** процедура **ИМ 40** (выпуск для внутреннего потребления) — она
покрывает основную массу коммерческого импорта. Экспорт (ЭК 10) — v1.1 (та же
механика, меньше платежей). Транзит, переработка, склад — вне скоупа.

**Не-скоуп (жёстко):**
- Подача ДТ в ЕАИС и любое взаимодействие с ЭЦП — делает человек в АРМ «Брокер».
- ДТС (декларация таможенной стоимости) как отдельный документ — v2.
- КДТ (корректировка) — v2.
- Гарантии/обеспечение (графы 50–53) — заполняются вручную при необходимости.

**Юридическая рамка:** каждый экспорт помечается «Проект документа. Подготовлен
программным средством, требует проверки декларантом». Ответственность за
поданные сведения несёт подписант — это отражается в оферте.

## 2. Термины

| Термин | Значение |
|---|---|
| **Досье (Shipment)** | Рабочее пространство одной поставки: стороны, документы, позиции, расчёты, проект ДТ |
| **Основной лист / добавочные** | ДТ = 1 товар на основном листе + по 3 товара на добавочных; максимум 999 товаров |
| **ФЛК** | Форматно-логический контроль — программные проверки заполнения (без LLM) |
| **R.055** | Идентификатор электронной структуры ДТ по Решению № 75 (XML) |
| **Каталог** | Товарный справочник компании: артикул → утверждённый код ТН ВЭД |

## 3. Пользовательский флоу

Wizard из 6 шагов поверх существующих компонентов (`frontend_spec.md`, сценарий B
расширяется до досье):

```
1. ДОКУМЕНТЫ          drag&drop: инвойс*, упаковочный, CMR/AWB/ЖД, контракт, сертификаты
                      → OCR (есть) → типизация документов (LLM) → извлечённые сущности
2. СТОРОНЫ И СДЕЛКА   продавец/отправитель, покупатель/получатель, декларант
                      (автоподстановка из OCR + справочник контрагентов; ИНН-проверка)
                      валюта, Incoterms, характер сделки, торгующая страна
3. ТОВАРЫ             таблица позиций (из инвойса): описание, количество, цена, вес
                      → классификация: каталог-хит (0 LLM) или каскад (needs_input inline)
                      → доп. единицы измерения, страна происхождения per-товар
4. ЛОГИСТИКА И        транспорт (18/21/25/26), места (6), контейнеры (19),
   СТОИМОСТЬ          фрахт/страховка до границы ЕАЭС → распределение по позициям
                      → таможенная стоимость (45) per-товар, курс НБКР (23)
5. ПРОВЕРКИ           ФЛК + кросс-сверка документов + риски (стоимость/кг, НТР,
                      разрешительные в 44, контрольные списки) → светофор по графам
6. ЭКСПОРТ            XLSX | PDF-форма | копи-режим | XML R.055 (M3) | JSON
```

**Статусная модель досье:**
`draft → extracting → classifying → needs_input → calculating → review(валидации) → ready → exported → archived`
(needs_input — существующий механизм; на уровне досье агрегирует item-level вопросы).

Каждый шаг сохраняется независимо; можно вернуться. Клонирование досье создаёт
копию со сброшенными документами, но сохранёнными сторонами/позициями (типовой
кейс «та же поставка, новый инвойс»).

## 4. Маппинг граф ДТ на источники

**C** — классификация (каскад/каталог); **R** — расчёт (движок, без LLM);
**K** — классификаторы (Решение 378 + локальные справочники); **U** — ввод/выбор
пользователя; **A** — автоконстанта для ИМ 40.

## 5. Расчётный движок (только код, ноль LLM)

### 5.1. Таможенная стоимость (метод 1)

```
ТС(товар) = Цена(42) × Курс(23)
          + доля(Фрахт до границы ЕАЭС)      ← если базис EXW/FCA/FOB…
          + доля(Страховка)                   ← если не включена в цену
          + доля(Погрузка/перегрузка до границы)
          − вычеты (фрахт после границы, если выделен в CIF/CIP/DAP…)
```

- Матрица Incoterms 2020 → какие расходы добавлять/вычитать (константная таблица
  11 базисов; для DAP/DDP — вычет внутренних расходов только при документальном
  подтверждении, иначе warning).
- Распределение общих расходов по позициям: по весу брутто (по умолчанию) или по
  стоимости — выбор пользователя, фиксируется в досье.
- Фрахт/страховка берутся из транспортного счёта (OCR) или вводятся одной суммой.

### 5.2. Графа 47: виды платежей для ИМ 40 (КР)

| Платёж | База | Ставка | Источник данных |
|---|---|---|---|
| Таможенные сборы за оформление | ТС / фикс | по НПА КР | **новый справочник** `customs_fees_kg` (наполнить из НПА; verify — см. §12) |
| Ввозная пошлина (ЕТТ) | ТС или ед. изм. | из `tnved_tree.duty_rate` | **нужен парсер ставок** (§5.3) |
| Акциз | ед. изм./ТС | `excise_rates` (ст. 336 НК КР) | есть |
| НДС | **ТС + пошлина + акциз** | 12% / освобождение | `vat_exemptions` (ст. 289 НК КР) — есть |

Коды видов платежей и способов уплаты — из классификаторов Решения 378
(+ национальные значения КР — verify в кастдеве по реальной ДТ).

### 5.3. Парсер ставок ЕТТ (новый компонент, критичный)

Сейчас `duty_rate` — строка («5%», «10% но не менее 0,5 евро за 1 кг», «2 евро
за 1 шт»). Для графы 47 нужен структурированный вид:

```json
{ "type": "ad_valorem | specific | combined_min | combined_plus",
  "advalorem_pct": 10.0,
  "specific_amount": 0.5, "specific_currency": "EUR", "specific_unit": "кг",
  "raw": "10%, но не менее 0,5 евро за 1 кг" }
```

Парсер — регулярки + словарь единиц; покрытие ≥99.5% из 13 279 листьев, остаток —
таблица ручных исключений. Комбинированная ставка требует курс EUR (тот же фид НБКР)
и вес/количество → ещё один источник needs_input («не хватает веса нетто для
расчёта пошлины»).

## 6. Данные: новые сущности и фиды

### 6.1. Ядро (PostgreSQL, дополнение к существующей схеме)

```sql
organizations(id, name, inn, okpo, address, country, kind: self|client|counterparty,
              broker_certificate_no, created_by_account, ...)
accounts / memberships(role: owner|declarant|viewer)            -- auth (H1)

product_catalog(id, org_id, sku, description, approved_code VARCHAR(10),
                classification_id FK, aliases TEXT[], attributes JSONB,
                approved_by, approved_at, usage_count, last_used_at)
UNIQUE(org_id, sku)

shipments(id, org_id, status, procedure_code DEFAULT '40', direction 'IM',
          seller_org, buyer_org, declarant_org, incoterms, incoterms_place,
          contract_currency, freight_amount, freight_currency, insurance_amount,
          allocation_method 'weight|value', rate_date, created_by, ...)

shipment_documents(id, shipment_id, kind: invoice|packing|cmr|awb|rail|contract|
                   cert_origin|permit|other, ocr_job_id FK, number, date,
                   extracted JSONB, file_ref)

shipment_items(id, shipment_id, position_no, sku, description_source,
               catalog_id FK NULL, classification_result JSONB,
               hs_code VARCHAR(10), origin_country, qty, qty_unit,
               price, net_kg, gross_kg, packages, supp_qty, supp_unit,
               customs_value NUMERIC, payments JSONB)

dt_drafts(id, shipment_id, version, graphs JSONB,      -- {"g01": ..., "g47": [...]}
          structure_version,                            -- версия R.055/257, §12
          validation_report JSONB, exported_formats TEXT[], created_at)

validation_findings(id, dt_draft_id, rule_code, severity: error|warning|info,
                    graph_ref, item_no NULL, message, details JSONB)
```

`dt_drafts.graphs` — единственный источник истины для экспортёров; версии
неизменяемы (правка = новая версия) — это даёт аудит-трейл «кто что поменял».

### 6.2. Классификаторы Решения 378 (новый фид → `data_catalog.md`)

Таблица `ref_classifiers(classifier_code, item_code, name_ru, valid_from, valid_to)`.
Минимальный набор для ИМ 40: процедуры, особенности перемещения, виды документов
(для 44), характер сделки (24), виды транспорта (25/26), условия поставки (20),
методы ОС (43), преференции (36), виды платежей и способы уплаты (47), валюты и
страны. Источник — актуальная редакция Решения 378 (ЕЭК публикует; парсинг из
приложений). Обновление — при каждом изменении Решения (мониторинг раз в месяц).

### 6.3. Курсы НБКР (новый фид)

`exchange_rates(date, currency, rate)` — ежедневная загрузка официальных курсов
НБКР (USD, EUR, CNY, RUB, KZT минимум). Используется в графах 23/45/46/47 и
landed-cost калькуляторе. Ретроспектива нужна (курс на дату регистрации).

### 6.4. Справочник таможенных органов КР (новый фид)

`customs_offices_kg(code8, name, kind: post|border|svh_zone)` — коды для граф
29/30/53. Источник: перечень пунктов таможенного оформления ГТС/info.trade.kg
(PDF «List of customs clearance checkpoints»), пополняется вручную.

### 6.5. Реестры TULPAR (M2, интеграционный фид)

Проверка разрешительного документа: поиск по номеру/ИНН/коду в публичных
реестрах swis2.trade.kg (сертификаты/декларации ТР ТС и ТР КР, СГР, лицензии).
Реализация: HTTP-поиск по запросу пользователя (не полная реплика реестра),
кэш 24 ч. Результат: `found | not_found | status_mismatch | code_mismatch`.

| R-01 | Цена/кг ниже типичного диапазона по коду → риск КТС; список документов для защиты стоимости |
| R-02 | Код 33 с низким confidence или «trap-код» → предложить ревью/обоснование |
| R-03 | Описание 31 недостаточно для кода 33 (LLM-проверка соответствия) |
| R-04 | Товар в национальном контрольном списке / экспортно-контрольных перечнях → «требуется разрешение» |
| R-05 | TULPAR: документ из 44 не найден / приостановлен / код не совпадает |
| R-06 | Аномалии: qty×unit_price ≠ line total в инвойсе; дубли позиций |

Источники R-01: сначала открытые диапазоны и собственная накопленная статистика;
индикативные показатели ГТС не публичны — не обещаем их.

## 9. Разделение LLM / код (принцип)

| Задача | Исполнитель |
|---|---|
| Типизация документа, извлечение полей, нечёткое сравнение сторон | LLM (structured output, существующий OCR-пайплайн level 98 расширяется схемами invoice/packing/cmr/contract) |
| Классификация позиций | Каскад (есть) / каталог (без LLM) |
| Генерация текста графы 31, объяснения findings | LLM light |
| Курсы, стоимость, распределение расходов, графа 47, ФЛК, экспорт | **Только код.** LLM запрещён в арифметике и правовых константах |
| Кросс-сверка чисел | Код (после LLM-извлечения полей) |

Это правило — в система-промпты и код-ревью: любое число в графах 12/23/45/46/47
должно быть воспроизводимо детерминированной функцией от входов.

## 10. Себестоимость проекта ДТ (уточнение к vision §6.2)

| Компонент | Вызовы | Сомы |
|---|---|---|
| OCR + структуризация 4 документов | 4 × (OCR + LLM medium) | 5–6 |
| Типизация/извлечение доп. полей | 1–2 × medium | 2–3 |
| Классификация: 10 позиций, 40% новых | 4 × каскад | 10–12 |
| Кросс-сверка + риск-советник | 2 × medium | 3–4 |
| Графа 31 генерация (10 позиций, батч) | 1 × light | 1–2 |
| Расчёты, ФЛК, экспорт | код | ~0 |
| **Итого** | | **21–27 сом** (~$0.25–0.31) |

Худший случай (30 позиций, всё новое, 8 документов): ~90–110 сом → лимит
«до 20 позиций» в PAYG-цене 300 сом защищает маржу; свыше — доплата за позицию.

## 11. Этапность

**M1 «Досье и черновик» (6–8 недель)**
Сущности §6.1; профиль организации; wizard шаги 1–4 и 6; OCR-пакет с типизацией;
классификация досье (batch + каталог); движок стоимости и 47 (с парсером ставок
§5.3); ФЛК F-01…F-10; экспорт XLSX + PDF + копи-режим.
DoD: design-партнёр делает реальную ДТ 10 позиций < 15 мин; XLSX переносится в
АРМ «Брокер» без возврата к исходникам.

**M2 «Проверки и память» (4–6 недель)**
Кросс-сверка X-01…X-06; ФЛК полный; риск-советник R-01…R-06; TULPAR-валидация;
клонирование досье; JSON API; справочники §6.2–6.4 в полном объёме.
DoD: ≥1 предотвращённая реальная ошибка на каждые 10 ДТ (по findings, принятыми
пользователем); auto-fill ≥75%.

**M3 «Форматы» (4 недели + неизвестность внешних систем)**
XML R.055 + XSD-валидация; версия структуры конфигурируемая; пилот загрузки
в KEDEN (КЗ-данные — отдельный проект) и/или АРМ «Брокер»; browser-extension
R&D (если кастдев подтвердит отсутствие импорта файлов).

## 12. Открытые вопросы и риски

1. **АРМ «Брокер»: есть ли импорт XML/XLS?** — вопрос №1 кастдева; определяет
   приоритет M3 vs копи-режим. (research-док §7)
2. **Ставки сборов за таможенное оформление КР** — найти действующий НПА,
   завести `customs_fees_kg`; до этого сбор в 47 помечается «проверить».
3. **Национальные коды видов платежей КР для графы 47** — снять с реальной ДТ
   в кастдеве.
4. **Версия структуры R.055 на момент M3** — правки Решения 75 выходят ежегодно
   (последняя известная — № 90 от 07.10.2025); в `dt_drafts.structure_version`
   фиксируем версию, экспортёр — версионируемый.
5. **Точность OCR на реальных документах** (сканы фур, рукописные CMR) — может
   потребовать fallback «ручной ввод таблицы позиций» (обязателен в M1 в любом
   случае).
6. **Право:** формулировки дисклеймеров и оферты — юрист до первого платного ДТ.
7. **Персональные данные** в графе 54/документах — политика хранения, шифрование
   файлов, срок хранения досье (предложение: 3 года = срок пост-контроля,
   настраивается организацией).
