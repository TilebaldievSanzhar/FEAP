## P1. Ложные needs_input на уровне L5 (12 кейсов)

### Суть проблемы

Каскад проходит L0→L1→L2→L3→L4 успешно, но на L5 (выбор 10-значного кода) LLM решает, что не хватает технического параметра, и заполняет `missing_parameters`. Оркестратор видит непустой `state.missing_parameters` и останавливает каскад с `needs_input`.

### Подтверждение в коде

**`level5.py:79-85`** — если `result.missing_parameters` непусто, код устанавливает `state.missing_parameters` и возвращает результат **без записи code_10**.

**`level5_subsubposition.jinja2:8`** — промпт прямо говорит: *«НЕ УГАДЫВАЙ технические параметры»*. Строка 14: *«Лучше запросить уточнение, чем дать неправильный код»*.

### Что запрашивает LLM (реальные примеры)

| Кейс | Товар | Дошёл до | Запрашивает | Обоснованность |
|------|-------|:--------:|-------------|:--------------:|
| M01 | Говядина мороженая обваленная | 020230 | Часть туши, таможенная стоимость/1000 кг, статус «высококачественная» | Частично обосновано (таможенная стоимость реально нужна для 8000 евро порога), но часть туши указана («обваленная») |
| M02 | Части курицы замороженные | 020714 | Тип отруба (четвертины/грудки/крылья), квота по Прим.4 | Обосновано — описание не уточняет тип отруба |
| M04 | Рис коричневый, нешлифованный | 100630 | Соотношение длины к ширине зерна | Избыточно — для бурого риса это редко критично |
| M08 | Печенье сладкое сухое | 190531 | Процент молочного жира | Обосновано — реально влияет на код |
| M22 | Свитер кашемировый | 611011 | Масса одного изделия (в граммах) | Избыточно — масса свитера не критична для 10-значного кода |
| M23 | Брюки хлопковые мужские | 620342 | Плотность ткани >200 г/м2 | Избыточно — LLM сам пишет «скорее всего 6203425900» |
| M32 | Компрессор воздушный | 841480 | Кол-во ступеней сжатия | Обосновано |
| H02 | МФУ лазерное | 844331 | Основная функция (копирование или печать) | Частично — описание говорит «МФУ», что подразумевает обе |
| H14 | Седан Toyota Camry гибрид | 870323 | Подтверждение «новый» (не б/у) | Избыточно — описание говорит «новый» |
| H26 | Яхта моторная 15 м | 890332 | Район плавания (морской/речной) | Обосновано |
| H29 | Грузовик КамАЗ дизель | 870423 | Дата производства для подтверждения «новый» | Избыточно — описание говорит «новый» |
| H05 | Сыр полутвёрдый 45% | 040690 | Сорт сыра (Гауда, Эдам и т.д.) | Обосновано (requires_clarification=true) |

### Классификация ложных остановок

**Категория A — Полностью ложные (6 кейсов)**: M04, M22, M23, H14, H29, M01 (частично)
LLM запрашивает параметры, которые либо уже есть в описании, либо не критичны для выбора кода.

**Категория B — Частично обоснованные (3 кейса)**: M02, M32, H02
Информации действительно не хватает для точного 10-значного кода, но можно выбрать наиболее вероятный код с пониженным confidence.

**Категория C — Действительно обоснованные (3 кейса)**: M08, H05, H26
Технический параметр реально влияет на код, и его нет в описании.

### Корневая причина

Промпт L5 слишком консервативен: *«Лучше запросить уточнение, чем дать неправильный код»*. Это побуждает LLM перестраховываться, даже когда параметр можно вывести из контекста или когда он не критичен.

### Рекомендация

1. **Изменить промпт L5**: добавить инструкцию «Если параметр можно обоснованно вывести из описания — выведи его сам. Запрашивай уточнение ТОЛЬКО если параметр критичен для кода И полностью отсутствует в описании.»
2. **Добавить в промпт**: «Перечитай карточку товара и описание. Если написано "новый", "мороженый", "обваленный" — это УЖЕ является ответом на возможный вопрос.»
3. **Добавить fallback в L5**: если `missing_parameters` установлен, но есть кандидат с confidence > 0.5 — всё равно записать `selected_code_10` и пометить `confidence` как пониженный, вместо остановки.

**Ожидаемый эффект**: +6-9 кейсов (категории A и B)

## P2. Ошибки кода 8/10 знаков при верной субпозиции (12 кейсов)

### Суть проблемы

Каскад определяет позицию и субпозицию верно, но на финальном шаге L5 выбирает неверный 8- или 10-значный код. Разница обычно 1-2 цифры.

| M25 | Сапоги кожаные | 6403999800 | 6403991100 | code_8 | Длина стельки / тип верха |
| M30 | Холодильник бытовой | 8418108001 | 8418102001 | code_10 | Объём камеры (встраиваемый vs отдельностоящий) |

### Корневая причина

На уровне L5 выбор 8-10 значного кода часто зависит от **числовых порогов** (объём, мощность, масса, ток) или **классификационных признаков** (тип экрана, назначение, действующее вещество). LLM не всегда корректно сопоставляет характеристики товара с порогами в текстах кодов.

### Анализ по типам ошибок

**Тип A — Числовые пороги (5 кейсов)**: M10, M34, M37, H08, M30
Код зависит от числового значения (мощность, ток, объём), которое есть в описании, но LLM выбирает неверный диапазон.

**Тип B — Классификационные признаки (5 кейсов)**: M06, M25, M36, H10, H13
Код зависит от качественного признака (тип верха обуви, назначение мебели, тип экрана), который LLM интерпретирует неверно.

**Тип C — Специфические знания (2 кейса)**: H27, M39
Нужны специфические знания (действующее вещество инсектицида, категория прицепа).

### Рекомендация

1. **Извлечение порогов из кодов**: Перед вызовом L5, программно извлечь из текстов дочерних кодов числовые пороги и передать их в промпт как структурированную таблицу: `[{code: "8501522001", threshold: "75 кВт < P ≤ 375 кВт"}, ...]`
2. **Усилить контекст L5**: Передавать пояснения к субпозициям (сейчас загружаются пояснения к позиции, но не всегда к субпозиции).
3. **Валидация выбранного кода**: После L5, проверить что `selected_code_10` реально существует в БД (`get_node_by_code`).

**Ожидаемый эффект**: +5-8 кейсов

## P3. Ошибки субпозиции при верной позиции (5 кейсов)

### Суть проблемы

L4 выбирает неверную 6-значную субпозицию. Ошибки происходят в позициях 5-6 кода.

### Конкретные случаи

| Кейс | Товар | Ожид. | Предсказ. | Разница |
|------|-------|:-----:|:---------:|---------|
| E30 | Картина маслом на холсте, 2024 г. | 970121 | 970191 | 21 = масло/темпера, 91 = прочие (>100 лет) — LLM решил что картина «прочая» |
| H03 | Шампунь для окрашенных волос | 330510 | 330590 | 10 = шампуни, 90 = прочие — LLM не распознал как шампунь |
| H18 | Дрон DJI Air 3, масса 720 г | 880622 | 880621 | 22 = >250 г, 21 = ≤250 г — ошибка по массе (720 г очевидно >250) |
| H19 | Грузовик-рефрижератор 8 т | 870422 | 870421 | 22 = >5 т, 21 = ≤5 т — 8 т очевидно >5 т |
| H30 | Bluetooth-колонка JBL Charge 5 | 851822 | 851822 | Верная субпозиция, ошибка на code_8 |

### Корневая причина

**Числовые пороги**: В 2 из 5 случаев (H18, H19) LLM выбирает неверный диапазон при ОЧЕВИДНОМ числовом значении. Дрон 720 г классифицирован как ≤250 г, грузовик 8 т — как ≤5 т. Это указывает на проблему извлечения числовых значений из описания товара на уровне L4.

**Семантическая путаница**: В 2 случаях (E30, H03) LLM не распознаёт категорию товара (картина маслом → «прочее», шампунь → «прочие средства для волос»).

### Рекомендация

1. **Числовые пороги в L4**: Аналогично L5, извлечь пороги из текстов субпозиций и передать в промпт. Добавить в промпт L4 инструкцию: *«Если субпозиции разделены числовым порогом (масса, мощность, длина), ОБЯЗАТЕЛЬНО сопоставь указанный параметр с порогом.»*
2. **Пояснения**: Пояснения к субпозициям содержат конкретные примеры (шампунь → 3305.10). Убедиться, что пояснения загружаются для L4.

**Ожидаемый эффект**: +3-4 кейса

## P4. Ложные needs_input на уровне L4 (3 кейса)

### Суть проблемы

Каскад проходит L0-L3, но на L4 LLM запрашивает параметры, останавливая классификацию.

| Кейс | Товар | Дошёл до | Запрашивает |
|------|-------|:--------:|-------------|
| M09 | Концентрат апельсинового сока | 2009 (L3) | Число Брикса (Brix) |
| M19 | Кожа КРС, хромовое дубление | 4104 (L3) | Тип среза (лицевая/спилок) |
| H20 | Пылесос аккумуляторный | 8508 (L3) | Мощность двигателя, объём пылесборника |

### Корневая причина

Те же проблемы, что в P1, но на уровне L4. Промпт L4 аналогично L5 разрешает остановку при недостатке параметров. В кейсе M09 (число Брикса) запрос действительно обоснован — это критический параметр для классификации соков. В кейсах M19 и H20 — частично обоснован.

### Рекомендация

Применить те же подходы, что для P1: добавить fallback с пониженным confidence, улучшить L0 для извлечения технических параметров.

**Ожидаемый эффект**: +1-2 кейса

## P5. Ошибки позиции — heading (2 кейса)

### Суть проблемы

Самые серьёзные ошибки: неверная 4-значная позиция на уровне L3.

### Кейс BENCH-E22: Алюминиевый профиль → конструкция

| | Значение |
|-|----------|
| Товар | Профиль алюминиевый полый 6063-Т5 для оконных рам, 6 м, стенка 1.5 мм |
| Ожидали | 7604 (Прутки и профили алюминиевые) |
| Предсказали | 7610 (Конструкции алюминиевые: двери, окна, рамы) |
| Confidence | 0.2 (модель не уверена!) |
| Ловушка | Да — 7610100000 в списке trap_codes |

**Корневая причина**: Описание содержит фразу *«для оконных и дверных рам»*, что сработало как триггер для позиции 7610 (двери/окна). Однако по ОПИ 1 товар — это **профиль** (полуфабрикат), а не **конструкция** (готовое изделие). Модель не применила принцип «классифицируй по тому, ЧТО товар есть, а не для ЧЕГО он предназначен».

**Рекомендация**: Добавить в промпт L3 инструкцию: *«Назначение товара (для чего используется) НЕ определяет классификацию. Классифицируй по физической природе товара: материал, форма, степень обработки. Полуфабрикат классифицируется как полуфабрикат, даже если указано его назначение.»*

### Кейс BENCH-H21: Повербанк → преобразователь

| | Значение |
|-|----------|
| Товар | Повербанк Li-Ion 20000 мАч, USB-C, быстрая зарядка |
| Ожидали | 8507 (Аккумуляторы электрические) |
| Предсказали | 8504 (Трансформаторы, статические преобразователи) |
| Confidence | 0.85 (модель уверена, но неправа!) |

**Корневая причина**: Повербанк содержит и аккумулятор (8507), и преобразователь напряжения (8504). Модель выбрала 8504 по функции «преобразование», хотя основной компонент — аккумулятор. Это ошибка ОПИ 3б (определение основного характера).

**Рекомендация**: В пояснениях к группе 85 явно указано, что повербанки относятся к 8507. Загрузить пояснения к группе 85 в RAG, чтобы L3 видел этот пример.

**Ожидаемый эффект**: +1-2 кейса

## P6. Backtrack exceeded — ошибка каскада (1 кейс)

### Кейс BENCH-E06: Кофе жареный → ошибка backtracking

| | Значение |
|-|----------|
| Товар | Кофе зерновой жареный, арабика, 1 кг, средняя обжарка, Колумбия |
| Ожидали | 0901210001 (Раздел II, Группа 09) |
| Статус | ERROR |
| Сообщение | *«Exceeded maximum backtracks (3). Last trigger: Группа 09 отсутствует в предоставленном списке выбора групп раздела IV»* |

### Анализ цепочки событий

1. **L1** выбрал Раздел **IV** (Готовые продукты) вместо **II** (Растительные продукты)
2. **L2** получил список групп раздела IV (16-24) — группы 09 (кофе, чай) там нет (она в разделе II)
3. LLM на L2 понял, что кофе не подходит ни под одну группу раздела IV → сгенерировал `backtrack_trigger`
4. Backtracker вернулся на L2 (группа), но **остался в разделе IV**
5. Три попытки — три backtrack — лимит исчерпан → ERROR

### Корневая причина

Ошибка на **L1** (выбор раздела). Кофе жареный однозначно относится к Разделу II (гр. 09), но L1 выбрал Раздел IV. При backtracking система пытается перебрать группы **внутри того же раздела**, вместо того чтобы **вернуться на L1 и сменить раздел**.

### Проверка в коде

**`backtracker.py:36-38`**: Функция `_infer_target_level` определяет уровень отката по длине `excluded_code`. Если LLM в backtrack_trigger пишет «группа 09 не найдена» с `excluded_code="09"` (2 символа), система откатывается на level=2 (группу), а не на level=1 (раздел).

Для отката на раздел, нужен `excluded_code` в формате римской цифры или пустая строка. Но LLM пишет код группы, и система остаётся на уровне группы.

### Рекомендация

1. **Добавить логику в backtracker**: Если backtrack на уровне L2 и excluded_code — это группа, которой нет в текущем разделе → автоматически эскалировать backtrack на L1.
2. **Альтернатива**: При повторном backtrack на том же уровне — автоэскалация на уровень выше (уже частично реализовано в строке 44, но не срабатывает для этого сценария).
3. **Проверить L1**: Почему «кофе жареный» попал в Раздел IV а не II? Возможно, слово «жареный» ввело в заблуждение (ассоциация с готовыми продуктами).

**Ожидаемый эффект**: +1 кейс (и предотвращение аналогичных ошибок)

## P7. Node not found — ошибка валидации (1 кейс)

### Кейс BENCH-H24: Куртка пуховая → несуществующий код

| | Значение |
|-|----------|
| Товар | Куртка пуховая Gore-Tex, наполнитель 90% гусиный пух / 10% перо |
| Ожидали | 6201400000 (Анорак/куртка из текстиля, пуховая) |
| Статус | ERROR |
| Сообщение | *«Subposition node not found: 620193»* |

### Корневая причина

LLM на уровне L4 выбрал субпозицию **620193**, которой не существует в дереве ТН ВЭД. Код 6201 имеет субпозиции 620111, 620112, 620113, 620119, 620120, 620130, 620140, 620190 — но не 620193. LLM «галлюцинирует» несуществующий код.

**`level5.py:24-26`**: Код делает `get_node_by_code(db, subposition_code)` и при `None` выбрасывает `ValueError`. Аналогичная проблема может быть на любом уровне при получении узла из БД.

### Рекомендация

1. **Валидация кода после каждого уровня**: После L3, L4, L5 проверять, что выбранный код существует в дереве БД. Если не существует — повторить вызов LLM с уточнением «код X не существует, выбери из списка: [...]».
2. **Передавать только реальные коды**: На L4 уже передаётся список дочерних узлов. Добавить в промпт жёсткое ограничение: *«Выбери ТОЛЬКО из представленных кодов. Не придумывай коды.»*

**Ожидаемый эффект**: +1 кейс

## P8. Попадания в ловушки (2 кейса, не считая E22 из P5)

### Кейс BENCH-H01: Набор для пикника → термосы

| | Значение |
|-|----------|
| Товар | Набор для пикника в изотермической сумке: столовые приборы, тарелки, стаканы, разделочная доска |
| Ожидали | 4202929800 (Сумки и чемоданы с текстильной поверхностью — прочие) |
| Предсказали | 9617000001 (Термосы и вакуумные сосуды) |
| Confidence | 0.2 |

**Корневая причина**: Составной товар (набор). LLM неверно определил основной компонент — выбрал «изотермическую сумку» → ассоциация с термосом (9617), вместо «сумка для переноски предметов» (4202). Ошибка ОПИ 3б.

### Кейс BENCH-M20: Пиломатериалы → ловушка по 10-значному коду

| | Значение |
|-|----------|
| Товар | Доска обрезная сосна, 50×150 мм, длина 6 м |
| Ожидали | 4407113409 |
| Предсказали | 4407113401 |

**Корневая причина**: Ошибка на уровне 10-значного кода. Разница в последней цифре — тип распила или размерная группа.

### Рекомендация

1. **Для составных товаров**: Усилить промпт L3 по ОПИ 3б — определить основной компонент по назначению всего набора, а не по одному элементу. Основная функция набора для пикника — переносить и хранить предметы → сумка (4202).
2. **Для ловушек на L5**: Улучшить контекст L5 (см. P2).

**Ожидаемый эффект**: +1 кейс
