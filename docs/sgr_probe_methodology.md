# SGR Probe — микроскоп для инспекции рассуждений модели

## Зачем нужен

Бенчмарк показывает **что** модель ответила неправильно. Probe показывает **почему**.

При оптимизации каскадного классификатора мы итеративно меняем SGR-поля (Schema-Guided Reasoning), промпты и формат контекста. Каждое изменение может улучшить одни кейсы и сломать другие. Полный бенчмарк (100 кейсов, ~40 мин) слишком медленный для тестирования гипотез.

Probe решает три задачи:

1. **Диагностика**: Видим содержимое SGR-полей — что именно модель написала в `product_type_assertion`, `branch_selection`, `parameter_threshold_match`. Это как смотреть на промежуточные слои нейросети вместо только на выход.

2. **Измерение стабильности**: Запуск одного кейса N раз показывает, ошибка стохастическая (flash-lite «промахнулась») или стабильная (системный дефект в контексте/схеме).

3. **Быстрый цикл итерации**: Изменил промпт → запустил 3 проблемных кейса за 2 минуты → видишь результат. Вместо 40-минутного бенчмарка.

## Аналогия с ML

Оптимизация SGR похожа на обучение модели, но вместо градиентов мы работаем с текстом:

| ML | SGR-оптимизация |
|---|---|
| Loss function | Accuracy на бенчмарке |
| Parameters | SGR-поля (имена, описания, порядок), промпт, формат контекста |
| Gradient | SGR-поля ошибочных кейсов (probe показывает, ГДЕ рассуждение сломалось) |
| Learning rate | Размер изменений (одно поле vs полная переработка) |
| Validation set | Canary — 15 ключевых кейсов |
| Training set | Полный бенчмарк — 100 кейсов |
| Overfitting | Few-shot под конкретный кейс ломает другие |

### Цикл оптимизации

```
1. Прогнать бенчмарк → найти ошибки
2. Probe ошибки → понять корневые причины через SGR-поля
3. Классифицировать причины (доменное знание? ОПИ? стохастика?)
4. Сформулировать гипотезу фикса
5. Применить фикс (промпт / SGR-поле / контекст)
6. Probe тех же кейсов → проверить, что фикс работает
7. Probe canary → проверить, что нет регрессии
8. Полный бенчмарк → измерить общий эффект
9. Повторить
```

Шаги 2-7 занимают минуты, не часы. Полный бенчмарк (шаг 8) запускается только когда probe подтвердил гипотезу.

## Как работает

Probe запускает **реальный каскад** — не мок и не симуляцию. Подключается к БД в Docker, строит контекст через `PromptAssembler`, вызывает Gemini API с текущими SGR-схемами. Единственное отличие от HTTP API — probe перехватывает и печатает полный `SubpositionResult` / `SubsubpositionResult` со ВСЕМИ полями, включая SGR.

```
benchmark case (JSONL)
    ↓
L0 Enrichment → product_card
    ↓
L1-L3 → section, group, position
    ↓
L4/L5 (target level) → ПОЛНЫЙ результат с SGR-полями
    ↓
Сравнение с ground truth + вывод диагностики
```

## Использование

### Предварительные требования

- Docker-контейнер с PostgreSQL запущен (`docker compose up -d db`)
- venv активирован с установленными зависимостями
- `.env` содержит `GEMINI_API_KEY` и настройки провайдера

### Probe одного кейса

```bash
# L4 — показать SGR-поля субпозиции
PYTHONUTF8=1 venv/Scripts/python.exe benchmark/scripts/probe.py \
    --case BENCH-E14 --level 4

# L5 — показать SGR-поля финального кода
PYTHONUTF8=1 venv/Scripts/python.exe benchmark/scripts/probe.py \
    --case BENCH-M23 --level 5
```

### Измерение стабильности

```bash
# 3 прогона одного кейса — стохастическая ошибка или стабильная?
PYTHONUTF8=1 venv/Scripts/python.exe benchmark/scripts/probe.py \
    --case BENCH-H24 --level 4 --repeat 3
```

### Probe нескольких кейсов

```bash
# Через запятую
PYTHONUTF8=1 venv/Scripts/python.exe benchmark/scripts/probe.py \
    --cases BENCH-E14,BENCH-H24,BENCH-M17 --level 4 --repeat 2
```

### Canary — 15 ключевых кейсов

```bash
# Быстрый тест: все 15 canary-кейсов на L4
PYTHONUTF8=1 venv/Scripts/python.exe benchmark/scripts/probe.py \
    --canary --level 4
```

### Показать промпт без вызова LLM

```bash
# Посмотреть, что именно отправляется модели
PYTHONUTF8=1 venv/Scripts/python.exe benchmark/scripts/probe.py \
    --case BENCH-E14 --level 4 --prompt-only
```

## Canary set — 15 кейсов

Кейсы выбраны так, чтобы покрыть все типы ошибок и служить индикатором регрессии:

| Категория | Кейсы | Зачем |
|---|---|---|
| L4: части vs целое | H20, H30, H13 | SGR routing должен фиксить |
| L4: text-match | E14, H24, M17 | Чувствительны к формату дерева |
| L4: пороги | H14, E10 | Числовые сопоставления |
| L5: подкоды | E03, M23, M25 | Тонкие различия на финальном уровне |
| Доменные | M09, M22 | Требуют знаний вне контекста |
| Регрессия | E01, M30 | Простые кейсы, ДОЛЖНЫ быть верными |

## Таксономия ошибок (обнаружена через probe)

Probe позволил выделить 5 типов корневых причин ошибок L4:

| Тип | Пример | Как диагностировать | Как чинить |
|---|---|---|---|
| **ОПИ 6 — уровни дефисов** | H24: 620140 vs 620193 | SGR верно находит «хим.нити», но selected = родительский код | Пример в промпте + улучшить формат дерева |
| **ОПИ 3б — наборы** | H03: набор → «прочие» вместо основного компонента | SGR type = «набор», но branch = «прочие» | Инструкция «набор → по основному компоненту» |
| **Доменное знание** | M17: канистра ≠ бутыль | SGR branch = «прочие», модель не знает что канистра = аналогичное | Few-shot пример |
| **Текстовая ловушка** | H02: 844331 «2+ функции» vs 844332 | SGR верно анализирует, но 844331 кажется «конкретнее» | Требует пояснений к субпозиции в контексте |
| **Стохастика** | E14, E10 | Ошибка при --repeat не воспроизводится | Confidence-based retry (Фаза 3) |
