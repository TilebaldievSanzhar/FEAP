# Frontend FEAP — дополнение: рабочее место декларанта (модуль ДТ)

> **Как читать этот документ.** Это **дополнение** к [`frontend_spec.md`](frontend_spec.md) — базовая спека (классификация, OCR-документы, дерево ТН ВЭД, меры НТР, дизайн-система, стек) остаётся в силе, существующие экраны **переделывать не нужно** (кроме навигации и шапки, см. §4). Здесь описан новый пласт продукта: авторизация, раздел «Декларации» (досье поставки → проект ДТ) и каталог товаров. Бэкенд уже реализован: +34 эндпоинта (26 ДТ + 8 auth), всего 56 роутов.

## 1. Продуктовый контекст: пивот к «рабочему месту декларанта»

Продукт больше не «классификатор с примочками», а рабочее место декларанта/брокера в КР. Классификация становится **встроенным шагом** большего флоу:

```
Досье поставки (данные сделки + позиции + документы)
   → классификация позиций (каскад LLM, уже есть)
   → проверки (извлечение из документов, кросс-сверка, риски)
   → ПРОЕКТ декларации на товары (графы, платежи, ФЛК)
   → экспорт XLSX / PDF / XML
   → человек подаёт сам через АРМ «Брокер» (вне продукта)
```

**Критично для UI — продукт готовит проект, но НЕ подаёт декларацию.** Подача — вне скоупа навсегда (лицензия, ЭЦП и ответственность — у человека). Каждый артефакт проекта ДТ несёт пометку «ПРОЕКТ» (в PDF — водяной знак, в XLSX — пометка на листах). Интерфейс не должен создавать иллюзию «отправки в таможню».

### 1.1. Принципы, которые обязан транслировать интерфейс

1. **Деньги считает только код.** Таможенная стоимость, пошлина, акциз, НДС (графа 47) — детерминированный расчёт, без LLM. В UI эти числа подаются как «расчёт», без ИИ-маркировки.
2. **LLM — по краям и всегда «предлагает».** Извлечение полей из документов, сопоставление сущностей, текст графы 31, советы, предложения правок — всё это *предложения*, которые человек явно применяет или отклоняет. Every LLM-блок в UI маркируется единым паттерном (см. §11.2) и никогда не меняет данные сам.
3. **needs_input вместо тихого занижения.** Если для расчёта не хватает данных (нет курса, нет веса для специфической ставки) — система не подставляет 0, а возвращает список `missing_parameters`. UI показывает «чего не хватает» как первоклассное состояние, а не ошибку.
4. **Роли.** `viewer` — читать и экспортировать; `declarant` — редактировать и запускать LLM-действия (они платные!); `owner` — плюс управление участниками. Кнопки записи/LLM для viewer скрываются или дизейблятся с тултипом «Недостаточно прав».
5. **Версионность.** Проекты ДТ не перезаписываются — каждая генерация создаёт новую версию. История версий видима.

## 3. Авторизация и организации

### 3.1. Модель

- Аккаунт (email + пароль) состоит в одной или нескольких **организациях** с ролью `owner | declarant | viewer`. Все данные (досье, каталог, драфты) скоупятся организацией.
- Токен: JWT Bearer, срок жизни по умолчанию 24 часа. **Refresh-токена нет**: по истечении — 401 → редирект на /login. Роль в токен не зашита, перечитывается на каждый запрос → смена роли/удаление участника действуют мгновенно.
- Переключение организации = запрос нового токена (`switch-org`).
- Бэкенд-режимы: `AUTH_MODE=required` (всё через логин) и `AUTH_MODE=optional` (dev: без токена работает «анонимная» организация). UI должен поддержать оба: в optional-режиме без входа показывается текущий бейдж «Тестовый режим», в required — гард на все роуты кроме /login, /register.

### 3.2. Контракты

```
POST /api/v1/auth/register   { email, password, name?, org_name? } → 201 TokenOut
POST /api/v1/auth/login      { email, password, org_id? }          → TokenOut | 401 | 403
GET  /api/v1/auth/me                                               → MeOut
POST /api/v1/auth/switch-org { org_id }                            → TokenOut (новый токен)

GET    /api/v1/orgs/current/members                     (owner)    → { items: MemberOut[] }
POST   /api/v1/orgs/current/members { email, role }     (owner)    → 201 | 404 «аккаунт не найден» | 409 «уже участник»
PATCH  /api/v1/orgs/current/members/{account_id} {role} (owner)    → 200 | 409 «последний owner»
DELETE /api/v1/orgs/current/members/{account_id}        (owner)    → 204 | 409 «последний owner»
```

```json
// TokenOut
{
  "access_token": "eyJ…",
  "expires_in": 86400,
  "account": { "id": "…", "email": "aida@broker.kg", "name": "Аида" },
  "org": { "id": "…", "name": "ОсОО «Брокер-Сервис»", "role": "owner" }
}
// MeOut = { account, org, orgs: OrgBrief[] }  — orgs: все организации аккаунта с ролями
```

### 3.3. Экраны

- **/login** — email, пароль, ссылка на регистрацию. Ошибка входа — всегда общая «Неверный email или пароль» (бэкенд не различает намеренно). Если аккаунт в нескольких организациях, вход идёт в основную; выбор — уже внутри, через переключатель.
- **/register** — email, пароль, имя (опц.), название организации (опц.; пусто → создаётся личная организация). Регистрация сразу возвращает токен → сразу в продукт, без подтверждения почты (MVP).
- **Аккаунт-меню в шапке** (заменяет бейдж «Тестовый режим» при активной сессии): имя/email, текущая организация + роль, переключатель организаций (список из `me.orgs`, смена = новый токен + полная инвалидация данных), пункты «Участники» (owner) и «Выйти».
- **/org/members** (owner-only): таблица участников (email, имя, роль, дата добавления), добавление по email существующего аккаунта (приглашений по почте нет — если 404, показать «Попросите коллегу зарегистрироваться»), смена роли, удаление. Guard: последнего owner нельзя понизить/удалить (409) — дизейблить с тултипом.

## 5. Список досье — /declarations

`GET /api/v1/shipments?status=&limit=&offset=` →

```json
{
  "items": [{
    "id": "…", "status": "draft", "procedure": "IM40",
    "buyer_name": "ОсОО «Импорт-Азия»",
    "items_count": 12, "items_without_code": 3,
    "created_at": "…", "updated_at": "…"
  }],
  "total": 27
}
```

- Таблица: покупатель, статус, товаров (с бейджем `без кода: N`, если N > 0), обновлено. Фильтр-чипы по статусу, пагинация (limit ≤ 200).
- Действия строки: открыть, **клонировать** (`POST /shipments/{id}/clone` → 201, копия без драфтов и без истории — для повторяющихся поставок; сразу переход в новое досье), удалить (подтверждение).
- Кнопка «Новое досье» (declarant+).

### Статусная модель досье

```
draft ──(запуск классификации)──► classifying ──(джоба финализировалась)──► draft
draft ──(сгенерирован проект ДТ)──► review (есть ошибки/нехватки) | ready (ФЛК чист)
```

`classifying` — живой статус с прогрессом (см. §6.4). Если batch-джоба классификации встала в `needs_input`, досье **остаётся** `classifying` до ответов на уточнения (существующий механизм ответов джобы) или отмены.

Цвета статусов (согласованы с уже принятой семантикой): `draft` — нейтральный, `classifying` — синий (анимированный), `review` — amber, `ready` — emerald.

## 6. Workspace досье — /declarations/$shipmentId

Центральный экран продукта. Рекомендуемая композиция — вкладки + постоянная правая колонка статуса:

```
┌ Досье · ОсОО «Импорт-Азия» · IM40 ····························· [Клонировать] [⋯] ┐
│ Вкладки:  Поставка │ Товары (12) │ Документы (4) │ Проверки │ Проект ДТ (v3)      │
├────────────────────────────────────────────────┬───────────────────────────────────┤
│                                                │  ПАНЕЛЬ СТАТУСА (sticky)          │
│   …контент вкладки…                            │  Статус: review                   │
│                                                │  Позиции: 12 · без кода: 3        │
│                                                │  Документы: 4 · извлечено: 3      │
│                                                │  Проект ДТ v3: has_errors         │
│                                                │  ⛔ 2 ошибки · ⚠ 5 предупреждений │
│                                                │  [Собрать проект ДТ]              │
│                                                │  [⬇ XLSX] [⬇ PDF] [⬇ XML]         │
└────────────────────────────────────────────────┴───────────────────────────────────┘
```

`GET /shipments/{id}` → `ShipmentOut { id, org_id, status, data: ShipmentIn, created_at, updated_at, latest_draft_id, latest_draft_version }`. Сохранение — **`PUT /shipments/{id}` с полным `ShipmentIn`, позиции заменяются целиком**: UX — единая форма с локальным draft-состоянием (Zustand persist, как в ExtractedProductsTable) и явной кнопкой «Сохранить»; построчных PATCH нет.

### 6.1. Вкладка «Поставка» (шапка ДТ)

Поля `ShipmentIn` (в скобках — графа ДТ, показывать её номер рядом с полем — декларанты думают графами):

**Стороны** — три карточки `PartyIn { name*, country (ISO-2), address, inn }`:
- Продавец/отправитель (гр. 2), Покупатель/получатель (гр. 8/9), Декларант (гр. 14; тумблер «совпадает с покупателем» — по умолчанию вкл., тогда поле схлопнуто).
- ИНН получателя: формат КР — 14 цифр (иначе warning F-11 в ФЛК; можно мягко подсветить прямо в форме).

**Сделка:**
- Процедура: `IM40` (пока единственная, показывать как фиксированный бейдж «ИМ 40 — выпуск для внутреннего потребления»).
- Торгующая страна (гр. 11), страна отправления (гр. 15), страна назначения (гр. 17, дефолт KG) — ISO-2 селекты.
- Incoterms (гр. 20): селект из 11 значений `EXW FCA FAS FOB CFR CIF CPT CIP DAP DPU DDP` + место.
- Характер сделки (гр. 24): код из классификатора Решения 378 (селект из справочника; бэкенд валидирует по F-09).
- Валюта контракта (гр. 22): ISO-3.
- Дата курса НБКР (гр. 23): дата, пусто = сегодня. Курс подтягивает бэкенд; если курса на дату нет — это станет `missing_parameters` при сборке.

**Доначисления к таможенной стоимости** (в валюте контракта; отдельная группа с пояснением «влияют на графу 45»):
- Фрахт до границы ЕАЭС, фрахт после границы (вычет, если выделен документально), страховка, прочие расходы (погрузка, лицензионные…).
- Метод распределения по позициям: «по весу брутто» (дефолт) | «по стоимости».
- Подсказка: при Incoterms группы E/F (EXW, FCA, FAS, FOB) нулевой фрахт даст предупреждение W-FREIGHT «риск занижения ТС».

**Транспорт:** вид транспорта на границе (гр. 25, код из классификатора), номера ТС (гр. 18/21), контейнер да/нет (гр. 19), всего мест (гр. 6; пусто = Σ мест позиций).

### 6.2. Вкладка «Товары» (позиции)

Таблица позиций (до 999). Колонки: №, описание, **код ТН ВЭД**, происхождение, кол-во, цена, нетто/брутто, SKU. Строка раскрывается в полную форму `ShipmentItemIn`:

```
description*  — описание товара (основа графы 31)
hs_code       — 10 цифр (гр. 33); пусто = «требует классификации»
origin_country — гр. 34 (ISO-2 или 'EU')
qty + qty_unit — коммерческое количество
price*        — цена позиции в валюте контракта (гр. 42)
net_kg (гр. 38) / gross_kg (гр. 35) / packages (мест)
supp_qty + supp_unit — доп. единица (гр. 41; если код требует — обязательна, F-07)
preference    — код преференции (гр. 36; классификатор; пусто = без льгот)
sku           — артикул, связь с каталогом
extra         — произвольные атрибуты (сюда пишется результат классификации)
```

**Источник кода — ключевой индикатор.** По `classification_ref`:
- `job_item:…` → бейдж «каскад» (+ confidence из `extra.classification.confidence`, если есть);
- `catalog:…` → бейдж «каталог» (утверждённый код компании);
- нет ref, код введён руками → бейдж «вручную».

**Автоподстановка из каталога:** при сохранении досье позиция с заполненным SKU и пустым кодом автоматически получает утверждённый код из каталога (бейдж «каталог»). В форме SKU — автокомплит через `GET /catalog/suggest?q=` (мин. 2 символа), выбор подсказки заполняет описание/код.

**Кнопка «Указать код вручную»** открывает мини-поиск по дереву/коду (реиспользовать существующий lookup) — не заставлять печатать 10 цифр вслепую.

### 6.3. Помощник графы 31 (LLM, per-позиция)

`POST /shipments/{id}/items/{position}/describe31` (position с 1) → `G31Out`:

```json
{
  "accepted": true,
  "text_ru": "Щётки зубные электрические Oral Pro X200, со встроенным аккумулятором…",
  "facts": [{ "id": "f1", "label": "Код ТН ВЭД", "value": "8509800000 (8509 80 000 0)", "source": "позиция досье" }],
  "facts_used": ["f1", "f3"],
  "missing_attributes": ["материал корпуса"],
  "rejection_reasons": [],
  "attempts": 1
}
```

UX: панель у позиции — предложенный текст, под ним факты (использованные подсвечены; это grounding-гарантия: каждая цифра текста подтверждена фактами), список «чего не хватает для полного описания». Кнопка **«Вставить в описание»** заменяет `description` в форме (человек затем сохраняет досье). Если `accepted=false` — текст показывается приглушённо с `rejection_reasons` («не прошёл проверку на достоверность, использовать с осторожностью»), кнопки вставки нет либо она с подтверждением.

### 6.4. Классификация позиций из досье

Кнопка в панели статуса / вкладке «Товары»: **«Классифицировать N позиций без кода»** →
`POST /shipments/{id}/classify` → `202 { job_id, status, enqueued, skipped, poll_url, items_url, events_url }` | `409` «нет позиций без кода».

- Прогресс — **реиспользовать существующий Jobs-UI целиком** (JobProgressBar, SSE/polling, BatchAnswerDialog для needs_input, ответы через существующий механизм джобы).
- По завершении коды **сами записываются в позиции** (write-back), досье возвращается в `draft` — данные на вкладке обновить.
- Ручные коды не перезаписываются. Отдельное opt-in действие «Переклассифицировать всё» (`?force=true`) — с явным подтверждением «перезапишет все коды, включая ручные».

### 6.5. Вкладка «Документы»

Документы досье — не то же самое, что OCR-задачи из существующего раздела: это привязанные к досье тексты, из которых LLM извлекает структуру, и которые формируют графу 44.

`GET /shipments/{id}/documents` → список `DocumentOut`. Привязка (`POST …/documents`):
- Диалог с двумя источниками (ровно один): **вставить текст** ИЛИ **выбрать из OCR-задач** (`ocr_job_id` + `file_index` — выбор завершённой OCR-задачи и файла внутри неё; мост к существующему разделу «Документы»).
- Поля: тип (`auto` — определит LLM | `invoice | packing | cmr | awb | rail | contract | cert_origin | permit | other`), номер, дата.

Карточка документа:

```
┌ invoice №INV-2024-15 · 12.03.2026 ── [извлечено] ─────────────────┐
│ источник: OCR-задача a1b2… (файл 0) · 14 203 символа              │
│ Типизация: invoice · confidence 0.94 · маркеры: «Commercial       │
│ Invoice», реквизиты продавца…                                     │
│ ▸ Извлечённые поля (по типу — см. ниже)                           │
│ Проверки итогов:  ✓ D-INV-01 Σ строк = итогу                      │
│                   ✗ D-INV-02 … (expected 12 400.00, actual 12 000)│
│ ⚠ Сенсоры: «в тексте обнаружена инструкция-инъекция…»             │
│ [Извлечь заново] [Проверить в TULPAR] [Удалить]                   │
└───────────────────────────────────────────────────────────────────┘
```

**Извлечение** (`POST …/documents/{doc_id}/extract?kind=`, declarant+, LLM):
- Статусы документа: `attached → extracted | needs_kind`. `needs_kind` = типизация не уверена → UI просит выбрать тип вручную (селект из `invoice | packing | cmr | contract | cert_origin` — только для этих пяти есть экстракторы) и повторить extract с `?kind=`.
- `doc_type`: `{ content_summary, type_markers[], kind, confidence, language }` — показывать, это объяснение «почему система решила, что это инвойс».
- `doc` — извлечённые поля, состав зависит от типа:
  - **invoice**: number, doc_date, seller/buyer `{name, country, address, inn}`, currency, incoterms(+place), payment_terms, `lines[{ line_no, description, sku, qty, qty_unit, unit_price, amount, origin_country }]`, total_amount, quality_notes[];
  - **packing**: lines `{…, packages, net_kg, gross_kg}`, packages_total, net_total_kg, gross_total_kg;
  - **cmr**: sender/receiver/carrier, места погрузки/разгрузки, номера ТС, places, gross_kg, attached_docs[];
  - **contract**: стороны, currency, incoterms, total_amount, payment_terms, validity, goods_summary;
  - **cert_origin**: form (СТ-1/A/EUR.1…), exporter/importer, origin_country, origin_criteria, hs_codes_mentioned[].
  - Все числа приходят **строками** — рендерить как есть, mono.
- `checks[]` — пересчёт итогов кодом: `{ check: "D-INV-01", status: "ok|mismatch|skipped", message, expected, actual }` — компактный список с иконками.
- `sensor_warnings[]` — детект инъекций в тексте документа; показывать заметно (security-warning стиль), это сигнал «LLM-извлечению из этого файла доверять осторожно».

**Проверка разрешительного (TULPAR)** — только для `permit`/`cert_origin` (иначе 409):
`POST …/documents/{doc_id}/verify-permit?force=` → `PermitCheckOut { status, detail, source: "format"|"registry", checked_at, cached }`.
Статусы: `format_invalid | format_ok | found | not_found | status_mismatch | code_mismatch | unavailable`. `found` — зелёный; `format_ok` — нейтральный («формат корректен, реестр не настроен/недоступен»); остальные — amber/red. Результат кэшируется 24 ч (`cached: true` + кнопка «Проверить заново» = force). Статус попадает в графу 44 драфта и в предупреждение W-TULPAR.

### 6.6. Вкладка «Проверки»: кросс-сверка и риск-советник

Две LLM-панели по кнопке (declarant+; результаты не персистятся — это «свежий взгляд» по запросу).

**Кросс-сверка** `POST /shipments/{id}/crosscheck` (409, если нет извлечённых документов — empty-state «сначала выполните извлечение на вкладке Документы»):

```json
{
  "findings": [{ "rule": "X-01", "severity": "warning", "graph": null,
                 "message": "Итог invoice №INV-15 (12400.00) расходится с суммой цен позиций досье (12000.00)",
                 "details": { "doc": "invoice №INV-15", "expected": "12400.00", "actual": "12000.00" } }],
  "parties": [{ "pair_id": "…:seller", "entity": "продавец (графа 2)",
                "doc_label": "invoice №INV-15",
                "doc_value": "Guangzhou Trading Co., Ltd, CN",
                "shipment_value": "ГУАНЧЖОУ ТРЕЙДИНГ КО ЛТД, CN",
                "verdict": "match", "match_confidence": 0.93,
                "reasoning": "транслитерация одного наименования" }],
  "invoice_lines": [{ "doc_line_no": 3, "shipment_position": 2,
                      "match_confidence": 0.88, "reasoning": "…" }],
  "dropped": ["parties …: verdict «match» с confidence 0.55 < 0.75 → uncertain"],
  "llm_used": true
}
```

- Числовые правила (считает код, severity всегда warning): X-01 итог инвойса ↔ Σ цен позиций (допуск 0,5 %); X-02 валюта инвойса/контракта ↔ гр. 22; X-03 нетто пакинга ↔ Σ нетто (допуск 2 %); X-04 брутто пакинга ↔ Σ брутто, места ↔ гр. 6; X-05 брутто CMR ↔ Σ брутто; X-06 Incoterms инвойса/контракта ↔ гр. 20.
- Сопоставление сторон: две колонки «в документе» / «в досье», вердикт `match` (зелёная галка) / `mismatch` (красный) / `uncertain` (серый «не удалось сопоставить»), confidence, причина. Ниже порога уверенности бэкенд сам понижает вердикт до uncertain — UI ничего не решает.
- Строки инвойса ↔ позиции: матрица/список «строка №3 → позиция 2», несопоставленные строки (`shipment_position: null`) — отдельным блоком «строки без пары».
- `dropped` — свёрнутый блок «отброшено контролем» (для доверия аудитора).

**Риск-советник** `POST /shipments/{id}/advise` → `AdviseOut`:

- `signals[]` (детерминированные эвристики, считает код): `{ id: "S-PRICEKG-2", kind, severity: "warning|info", message, data }`. Виды: `S-PRICEKG-n` — цена/кг выбивается из медианы досье (нужно ≥3 позиций с весом); `S-NONET-n` — нет веса нетто; `S-NETGROSS-n` — нетто = брутто; `S-LOWCONF-n` — уверенность классификации < 0.6.
- `advices[]` (LLM-пояснения к сигналам): `{ signal_id, explanation, evidence: [{source, detail}], recommendation }` — карточка «что это значит при контроле» + «что сделать до подачи».
- `code_checks[]` (LLM, соответствие описания коду по каждой позиции с кодом): `{ position, verdict: "consistent|questionable|mismatch", reasoning }` — список позиций с вердикт-иконкой; `questionable`/`mismatch` — повод перепроверить код (ссылка на позицию).

### 6.7. Вкладка «Проект ДТ»

**Генерация:** кнопка «Собрать проект ДТ» → `POST /shipments/{id}/dt-draft` → 201, новая версия. История версий (v1, v2, …) — селектор; открытая версия — `GET /dt-drafts/{id}`:

```json
{
  "id": "…", "shipment_id": "…", "version": 3,
  "status": "has_errors",              // ready | has_errors | needs_input
  "structure_version": "257-print/1",
  "graphs": { "meta": {…}, "header": {…}, "items": [{…}], "totals": {…} },
  "findings": [{ "rule": "F-04", "severity": "error", "graph": "g22",
                 "message": "Σ цен позиций (12000.00) расходится с графой 22 (12400.00) на 3.23% (> 0.5%)",
                 "details": {…} }],
  "missing_parameters": ["Товар 2 (8509800000): вес нетто для специфической ставки"],
  "created_at": "…"
}
```

**Просмотр граф** — главный «вау-экран»: макет, узнаваемый декларантом как ДТ (печатная логика Решения 257), а не JSON.

- `header` (графы шапки): `g01 {direction:"ИМ", procedure:"40", form:"ЭД"}`, `g02` продавец, `g03 {sheets}` листы, `g05` всего товаров, `g06` мест, `g07` номер досье, `g08/g09` получатель, `g11` торгующая страна, `g12` общая таможенная стоимость, `g14` декларант, `g15/g17` страны, `g18/g21` номера ТС, `g19` контейнер, `g20 {incoterms, place}`, `g22 {currency, amount}`, `g23 {rate, date}` курс, `g24` характер сделки, `g25` вид транспорта, `g37 {requested:"40", previous:"00", feature:"000"}`.
- `items[]` (по каждому товару): `g32` №, `g31 {description, qty, qty_unit, packages, sku}`, `g33` код, `g34` происхождение, `g35` брутто, `g36` преференция, `g38` нетто, `g41 {qty, unit, required_unit}` доп. единица, `g42` цена, `g43` "1", `g44` документы `[{code, kind, number, date, permit_status?}]` (код вида документа по Решению 378; общие документы досье повторяются в каждом товаре — это практика заполнения), `g45` таможенная стоимость, `g46` статистическая стоимость USD, `g47` платежи.
- `g47` — таблица расчёта по товару, строки `{ kind: "duty|excise|vat|fee", code: "2010|4010|5010|1010", basis, rate, amount, missing[], note }`. Если `amount = null` — вместо суммы показывать «не рассчитано» + список `missing` (что нужно донести). **Не прятать missing — это фича.**
- `totals`: `g05`, `g03_sheets`, `g12`, `invoice_total`, `additions_total`, `payments {duty, excise, vat, fee}`, `fee_line` (сбор за оформление; может отсутствовать → W-FEE info). Итоговая карточка «К уплате (проект)»: пошлина + акциз + НДС + сбор, крупно, в сомах.
- Все суммы приходят **строками** (Decimal) — не парсить в float, рендерить как есть (можно группировать разряды), моноширинно.

**Панель ФЛК (findings)** — постоянно видимая рядом с графами (правая колонка или нижняя панель):

- Finding: `{ rule, severity: error|warning|info, graph: "g22" | "items[2].g38" | null, message, details }`. `graph` — **кликабельный якорь**: клик подсвечивает соответствующую графу/поле. Группировка: ошибки → предупреждения → инфо; счётчики в заголовке вкладки и панели статуса.
- Смысловые группы правил (для тултипов/легенды):
  - `F-01` обязательные графы · `F-02` счётчики листов/товаров · `F-03` код существует и является конечным · `F-04` Σ цен = графа 22 (±0,5 %) · `F-05` Σ гр. 45 = гр. 12 · `F-06` нетто ≤ брутто · `F-07` доп. единица обязательна · `F-08` валюта/курс корректны · `F-09` коды по классификаторам Решения 378 · `F-10` арифметика графы 47 (включая базу НДС = ТС + пошлина + акциз) · `F-11` формат ИНН КР (warning) · `F-13` преференция требует документа в гр. 44 · `F-14` по коду есть меры НТР — нужен разрешительный (warning, со ссылкой на существующий экран НТР) · `F-15` даты документов (warning)
  - `W-31` описание товара короче 30 символов · `W-FREIGHT` базис требует фрахта, а он нулевой (риск КТС) · `W-FEE` сбор за оформление не настроен (info) · `W-TULPAR` разрешительный не подтверждён реестром.
- `status = needs_input` → сверху панели блок «Не хватает данных»: список `missing_parameters` с кнопкой-переходом к соответствующему полю досье.

**Предложения правок (fixer, LLM)** — кнопка «Предложить исправления» на панели findings → `POST /dt-drafts/{id}/fix-suggestions` → `FixOut`:

```json
{
  "analysis": "Большинство ошибок — расхождение сумм из-за незаполненного фрахта…",
  "suggestions": [{
    "finding_rule": "F-04", "finding_graph": "g22",
    "action": "propose_value",                    // | ask_user | cannot_fix
    "field_path": "freight_to_border",            // поля досье; items[0].net_kg — индекс с 0
    "proposed_value": "400.00",
    "question": null,
    "why": "Инвойс №INV-15 содержит строку Freight: 400.00 USD",
    "evidence": ["invoice №INV-15: total_amount…"],
    "verification": { "applied": true, "verified": true,
                       "errors_before": 2, "errors_after": 1,
                       "status_after": "has_errors", "note": null }
  }],
  "llm_used": true
}
```

UX — карточки предложений (единый паттерн §11.2):
- `propose_value` + `verification.verified: true` → бейдж «✓ проверено пересборкой» + кнопка **«Применить»**: правит соответствующее поле формы досье → PUT → предложение перегенерировать драфт. `verified: false` → приглушённая карточка с `note` («finding не исчез» / «правка добавляет новые ошибки»), применять можно, но с предупреждением.
- `ask_user` → карточка-вопрос с инлайн-полем ответа → ответ вписывается в нужное поле досье человеком.
- `cannot_fix` → пояснение, почему нужно решать вне системы.
- Применение всегда явное, по одному предложению; «Применить все verified» — допустимая массовая кнопка с итоговым diff-подтверждением.

**Экспорт** (любая роль): три кнопки скачивания на панели статуса и вкладке драфта.
- `GET /dt-drafts/{id}/export.xlsx` — книга с 4 листами (шапка/товары/платежи/проверки), везде пометка «ПРОЕКТ».
- `GET /dt-drafts/{id}/export.pdf` — печатная форма с водяным знаком «ПРОЕКТ»; `501` = на сервере нет кириллического шрифта → тост с текстом ошибки.
- `GET /dt-drafts/{id}/export.xml` — XML структуры `R.055-draft` (честно предварительная, до пилота с АРМ «Брокер»/KEDEN); `422` = не прошёл XSD → диалог со списком `errors[]` (до 20), файл не скачивается. Рядом с кнопкой XML — маленькая пометка «предварительная структура».

## 7. Каталог товаров — /catalog

«Золотые записи» компании: SKU → утверждённый 10-значный код. Смысл: повторные поставки не гоняются через LLM-классификацию (экономия и предсказуемость), код появляется в досье автоподстановкой.

- `GET /catalog?q=&limit=&offset=` → `{ items: [{ id, sku, description, hs_code, attributes, usage_count, approved_by, approved_at, created_at, updated_at }], total }`.
- Таблица: SKU, описание, код (mono, с форматированием `8509 80 000 0`), атрибуты (chips), использований, кем/когда утверждён. Поиск по SKU и описанию.
- Создание/правка (declarant+): `POST /catalog` — upsert по SKU (объяснить в UI: «повторный SKU обновит запись»). Поля: sku*, description*, hs_code (10 цифр, опц.), attributes (key-value), approved_by.
- Удаление — `DELETE /catalog/{id}` с подтверждением.
- **«Импорт из досье»** — ключевое действие-утверждение: в workspace досье (вкладка «Товары», после классификации) кнопка «Утвердить коды в каталог» → `POST /catalog/import-from-shipment/{shipmentId}` → `{ imported, updated, skipped }` (skipped = позиции без SKU или без кода) → тост-сводка. Это единственный путь, которым LLM-коды попадают в каталог — подача действия в UI должна подчёркивать, что это **утверждение человеком** (например, диалог со списком переносимых SKU→код и галочками).

## 9. Ошибки и состояния (обязательные к дизайну)

| Код | Когда | UX |
|---|---|---|
| 401 | нет/протух токен | required-режим: редирект на /login с возвратом; optional: остаёмся в анонимном режиме |
| 403 | недостаточная роль | тост «Недостаточно прав (нужна роль declarant)»; лучше — не показывать кнопку вовсе |
| 404 | нет объекта ИЛИ объект чужой организации | единый экран «Не найдено» (бэкенд намеренно не различает) |
| 409 | конфликты домена | текст из `detail` как есть: «нет позиций без кода», «сначала выполните extract», «последний владелец», «тип документа не разрешительный», email/членство заняты |
| 422 | валидация; XSD; неверный kind | инлайн у полей формы; для XML — диалог со списком ошибок |
| 501 | PDF без кириллического шрифта | тост с текстом |
| 202 | classify | переход в режим прогресса (Jobs-UI) |

Плюс доменные состояния: `needs_kind` у документа, `needs_input` у драфта (missing_parameters), `classifying` у досье, `uncertain`-вердикты сверки, невалидированный XML, `verified:false` у предложений fixer'а.

## 11. Дизайн-указания для новых экранов

### 11.1. Общее
- Та же дизайн-система (токены `--bg/--primary/--warn-*`, сайдбар 240 px, существующая типографика; коды и деньги — mono).
- Плотность — «рабочий инструмент»: таблицы компактные, много данных на экране, прогрессивное раскрытие деталей.
- Номера граф ДТ — часть языка пользователя: показывать «(гр. 22)» у полей и «g22»-якоря в findings.

### 11.2. Паттерн «ИИ-предложение» (единый для всего модуля)
Один узнаваемый компонент для: fixer-предложений, текста графы 31, советов риск-советника, вердиктов сопоставления сущностей:

```
┌ ✦ ИИ-предложение ─ [✓ проверено пересборкой]┐
│ <суть предложения / текст>                  │
│ Почему: <why>                               │
│ Основание: <evidence, свёрнуто>             │
│ [Применить]   [Отклонить]                   │
└─────────────────────────────────────────────┘
```

Правила: ИИ-контент всегда визуально отделён от расчётных данных; всегда есть «почему» и «основание»; применение — только явным действием; отброшенное harness-контролем (`dropped`) доступно в свёрнутом виде.

### 11.3. Паттерн «Findings-панель»
Единый список для ФЛК (F/W), кросс-сверки (X) и проверок документов (D): иконка severity (`error` красный / `warning` amber / `info` серый-синий), код правила как chip с тултипом-расшифровкой, message, опциональный якорь на графу/поле, `details.expected/actual` — в раскрытии.

### 11.4. Статусы (расширение существующей семантики)
- Досье: `draft` нейтральный · `classifying` синий · `review` amber · `ready` emerald.
- Проект ДТ: `ready` emerald · `has_errors` красный · `needs_input` amber (= той же семантики, что needs_input классификации).
- Документ: `attached` нейтральный · `needs_kind` amber · `extracted` emerald.
- TULPAR: `found` emerald · `format_ok` нейтральный · `unavailable` серый · остальное amber/red.
- Вердикты: `match/consistent` emerald · `uncertain/questionable` amber · `mismatch` red.

### 11.5. «ПРОЕКТ, не подача»
На вкладке «Проект ДТ» и в диалогах экспорта — постоянный ненавязчивый бейдж/подпись: «Проект декларации. Подача — через АРМ „Брокер“ самостоятельно». Никаких кнопок «Отправить», «Подать».

## 12. Приоритеты дизайна

**P0 — ядро ценности:**
1. Auth: /login, /register, аккаунт-меню, гарды, анонимный optional-режим.

## 13. Не-цели (не проектировать)

## 14. Открытые вопросы к дизайну

1. **Композиция workspace**: вкладки (рекомендовано выше) или единый длинный скролл с секциями? Досье с 100+ позициями делает скролл тяжёлым.
2. **Просмотр граф**: имитировать печатный бланк ДТ (узнаваемость) или «карточно-табличный» современный вид (читаемость)? Рекомендация — карточно-табличный с номерами граф, без пиксельной имитации бланка.
3. Где живут кросс-сверка и советник: отдельная вкладка «Проверки» (рекомендовано) или блоки внутри «Документов»/«Проекта ДТ»?
4. Пустые состояния: первое досье (онбординг «создайте досье → добавьте товары → соберите проект»), пустой каталог (подсказка про «Утвердить из досье»).
5. Название раздела: «Декларации» vs «Досье» vs «Поставки» — нужно решение по терминологии с пользователями-декларантами.
