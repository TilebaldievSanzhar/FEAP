# Миграция на PDF ЕЭК как единственный источник дерева ТН ВЭД

## Мотивация

### Проблема текущего подхода (v3: TWS + ФНС + LCP)

Для построения дерева ТН ВЭД с именами узлов используются **3 неполных источника данных** и **2 кастомных алгоритма**, каждый со своими проблемами:

| Источник | Что даёт | Проблема |
|----------|----------|----------|
| TWS Excel (tws.by) | 13,279 листьев, ставки, `name_parts` через `🠺` | Переменная глубина путей, не маппится на уровни ТН ВЭД |
| ФНС TNVED4.TXT (nalog.gov.ru) | Имена субпозиций, dash-level | Виртуальные узлы не записаны отдельно, только dash-level у листьев |
| LCP-алгоритм (наш код) | Вывод имён из пересечений name_parts | Хрупкий, баги на стыке с ФНС, 15% не покрывает |

Результат: **17.1% позиций** (164 из 1,228) имеют субпозиции с дублирующимися именами. LLM на уровне L4 получает список вариантов, где несколько пунктов называются одинаково — выбор невозможен.

Подробный анализ: [docs/naming_problem.md](naming_problem.md)

### Корневая причина

Номенклатура ТН ВЭД содержит **виртуальные промежуточные узлы** между позицией (4 цифры) и субпозицией (6 цифр). Они обозначены дефисами в официальном тексте, но не имеют собственных кодов:

```
0802 Прочие орехи
├── [– миндаль:]                   ← виртуальный, нет кода
│   ├── 0802 11  – – в скорлупе
│   └── 0802 12  – – очищенный
├── [– орех лесной:]               ← виртуальный, нет кода
│   ├── 0802 21  – – в скорлупе    ← дубликат без контекста!
│   └── 0802 22  – – очищенный
```

Ни TWS Excel, ни ФНС TNVED4 не содержат тексты этих виртуальных узлов как отдельные записи. Единственный источник, где они есть — **официальный PDF номенклатуры ЕЭК**.

### Почему не продолжать гибридный подход

1. **Хрупкость при обновлении** — при ежегодном обновлении номенклатуры нужно синхронизировать 3 источника, прогнать 4 скрипта в правильном порядке, проверить что LCP не сломался на новых данных
2. **Баг на стыке FNS↔LCP** — уже есть 8 случаев, где LCP перезаписывает уникальное ФНС-имя (кросс-проверка отсутствует)
3. **Потолок** — даже с идеальным гибридом остаётся ~8% нерешаемых дубликатов (158 групп, где TWS-путь тоже не различает сиблингов)
4. **Сложность поддержки** — 3 парсера, 2 алгоритма вывода имён, комбинированная стратегия с fallback-цепочкой

---

## Решение: PDF ЕЭК как единственный источник дерева

### Принцип

```
PDF ЕЭК (официальная номенклатура)
  └── один парсер → полное дерево со ВСЕМИ именами (включая виртуальные узлы)

TWS Excel (tws.by)
  └── только ставки пошлин + единицы измерения
  └── мержатся к листьям дерева по 10-значному коду
```

Один авторитетный источник для дерева и имён → один парсер → 100% покрытие → нет костылей.

### Структура содержимого PDF — подтверждено

Каждый PDF — табличный документ с колонками:
1. Код ТН ВЭД (4, 6, 8, 10 цифр)
2. Наименование позиции (с дефисной иерархией)
3. Доп. единица измерения
4. Ставка ввозной таможенной пошлины

Типы строк в колонке «Наименование»:

| Тип строки | Пример | Как распознать |
|-----------|--------|----------------|
| Позиция (4 цифры) | `0802  Прочие орехи...` | Regex `^\d{4}\s*$` + текст на следующих строках |
| Субпозиция header (6 цифр) | `0802 11` | Regex `^\d{4}\s\d{2}\s*$` |
| Лист (10 цифр) | `0802 11 100 0  – – – горький` | Regex `^\d{4}\s\d{2}\s\d{3}\s\d` |
| **Виртуальный узел** | `– миндаль:` | Начинается с `–` (U+2013), без кода |

Виртуальные узлы имеют уровень вложенности, обозначенный количеством дефисов:
- `–` = 1-dash (первый уровень под позицией)
- `– –` = 2-dash (второй уровень)
- `– – –` = 3-dash и т.д.

Максимальная глубина виртуальных узлов — до 6 уровней (группа 84).

### Нюансы парсинга, выявленные при тестировании

1. **Многострочные наименования** — имя позиции/листа может занимать 2–4 строки. Парсер должен склеивать строки до следующего кода или дефисной строки.

2. **Одиночный `–` в столбце ставки** — символ `–` используется как «нет данных» в колонке ставок. Нужно отличать от дефисов иерархии. Решение: виртуальный узел = `–` + текст длиннее 2 символов.

3. **Заголовки таблицы на каждой странице** — строки «Код ТН ВЭД», «Наименование позиции», «Ставка ввозной...» повторяются. Нужно фильтровать.

4. **8-значные коды** — некоторые строки содержат `0802 91 000` (без последней цифры) как промежуточный header. Это 8-значный уровень, нужно обрабатывать.

5. **Формат имени субпозиции** — для субпозиций, у которых есть виртуальный родитель, финальное имя строится как `"виртуальный_родитель > собственное_имя"`. Если виртуальных уровней несколько, можно использовать только ближайший 1-dash родитель (достаточно для уникальности в большинстве случаев) или полную цепочку.

6. **Привязка виртуальных узлов к субпозициям** — виртуальный узел действует на все листья/субпозиции, идущие после него до следующего виртуального узла того же или меньшего dash-level (стек).

## Архитектура нового пайплайна (v4)

### Схема данных

```
[Скачивание]
  eec.eaeunion.org/comission/department/catr/ett/
       │
       ▼
  data/ett_pdfs/ru.01.pdf ... ru.97.pdf    (96 файлов, ~50 MB)
       │
       ▼
[Парсинг PDF]
  scripts/parse_ett_nomenclature.py
       │  PyMuPDF (fitz) → извлечение текста
       │  Regex → распознавание строк (код/виртуальный/текст)
       │  Стек → привязка виртуальных родителей к кодам
       │
       ▼
  data/parsed/nomenclature.json            (полная иерархия)
       │
       ▼
[Сборка дерева]                    [Парсинг ставок]
  scripts/build_tree.py              scripts/parse_excel.py
       │                                  │
       │  nomenclature.json               │  TWS Excel
       │  + sections.json                 │
       │  + rates (из Excel)              ▼
       │◄─────────────────────── data/parsed/leaves.json

       ▼

```

## Порядок реализации

### Этап 1: Скачивание PDF

1. Написать `scripts/download_ett_pdfs.py`
2. Скрипт парсит страницу ЕЭК (или использует захардкоженный список URL — он стабилен)
3. Скачивает 96 PDF в `data/ett_pdfs/`
4. Проверяет целостность (размер > 0, PDF валиден)

### Этап 2: Парсер PDF → nomenclature.json

1. Написать `scripts/parse_ett_nomenclature.py`
2. Для каждого PDF:
   - Извлечь текст через PyMuPDF
   - Распознать строки: позиции (4 цифры), субпозиции (6 цифр), листья (10 цифр), виртуальные узлы (дефисы без кода)
   - Вести стек виртуальных родителей по dash-level
   - Склеивать многострочные наименования
   - Фильтровать заголовки таблицы и строки ставок
3. Собрать все группы в единый `nomenclature.json`
4. Валидация: сверить количество позиций, субпозиций и листьев с текущим `tree.json`

### Этап 3: Переработка build_tree.py

1. Убрать все функции вывода имён: `infer_parent_name()`, `_lcp()`, `_infer_name_by_lcp()`
2. Убрать загрузку `fns_names.json`
3. Добавить чтение `nomenclature.json`
4. Имена берутся напрямую из `nomenclature.json`:
   - Группы → `nomenclature.groups[code].name`
   - Позиции → `nomenclature.positions[code].name`
   - Субпозиции → `nomenclature.subpositions[code].full_name`
   - Листья → `nomenclature.leaves[code].name` или TWS Excel `name_leaf` как fallback
5. Ставки по-прежнему из TWS Excel (через `leaves.json`)

### Этап 4: Валидация

1. Пересобрать `tree.json`
2. Сверить с текущим `tree.json`:
   - Количество узлов на каждом уровне должно совпадать
   - Все 10-значные коды должны присутствовать
   - Ставки и единицы измерения не должны измениться
3. Проверить уникальность имён субпозиций:
   - Ожидание: **близко к 100%** (vs текущие 82.9%)
4. Прогнать бенчмарк классификации (если готов)

### Этап 5: Удаление старого кода

1. Удалить `scripts/parse_fns_reference.py`
2. Удалить `data/reference/fns_names.json`
3. Удалить `data/reference/TNVED.zip` и `data/reference/tnved_fns/`
4. Обновить `README.md` — убрать упоминания ФНС, обновить пайплайн
5. Обновить `CLAUDE.md` — если есть упоминания ФНС/LCP

## Обновление номенклатуры (ежегодный процесс)

Номенклатура ТН ВЭД обновляется решениями ЕЭК (обычно раз в год, вступает в силу с 1 января).

### Текущий процесс (v3) — 5 шагов, 3 источника

```
1. Скачать новый TWS Excel с tws.by
2. Скачать новый TNVED.zip с nalog.gov.ru
3. Запустить parse_fns_reference.py
```

## Риски и ограничения

### Риск 1: Изменение формата PDF

ЕЭК может изменить формат/вёрстку PDF. Маловероятно (формат стабилен с 2022), но возможно.

**Митигация:** парсер должен иметь валидацию — проверять, что количество извлечённых позиций и листьев соответствует ожидаемому. При значительном расхождении — ошибка, а не тихий пропуск.

### Риск 2: PDF недоступен

Сайт ЕЭК может временно быть недоступен.

**Митигация:** PDF скачиваются разово и хранятся в `data/ett_pdfs/`. Парсинг работает с локальными файлами. Скачивание — отдельный шаг, не блокирующий остальной пайплайн.

### Риск 3: Рассинхронизация PDF и TWS Excel

PDF ЕЭК и TWS Excel могут быть обновлены в разное время.

**Митигация:** merge по 10-значному коду. Если код есть в PDF, но нет в Excel — ставка пустая (допустимо). Если код есть в Excel, но нет в PDF — warning (нужно обновить PDF).

### Ограничение: PDF не содержит ставки

PDF содержит ставки пошлин, но они встроены в табличную вёрстку и сложнее извлекаются (смешаны с единицами измерения). TWS Excel — более надёжный источник ставок.

**Решение:** ставки по-прежнему из TWS Excel. PDF используется только для дерева и имён.
