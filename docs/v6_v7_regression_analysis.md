# Анализ регрессии: почему v7 хуже v6

**Дата анализа**: 2026-03-20
**v6**: 62/100 (heading 80%), запуск 2026-03-18
**v7**: 58/100 (heading 78%), запуск 2026-03-19
**Дельта**: -4 кейса (62 → 58), heading -2%

---

## Краткий вердикт

Результаты v7 ухудшились по трём независимым причинам:

1. **3 из 7 регрессий — ошибки Gemini API 503** (не связаны с кодом вообще)
2. **3 новых needs_input — fallback-логика не срабатывает** из-за того, что Gemini flash-lite не заполняет `selected_code_10` при наличии `missing_parameters`
3. **1 реальная классификационная регрессия** (E10) — нестабильность LLM

При этом **3 P-фикса сработали**: E06 (+1), H20 (+1), M19 (+1). Ещё 2 кейса (H05, H26) начали завершаться вместо остановки, но с неверным кодом.

**Если исключить ошибки API**: v7 = 61/100 vs v6 = 62/100 (дельта всего -1).

## Детальный разбор причин

### Причина 1: Ошибки Gemini API 503 (3 кейса)

**Кейсы**: E02, M29, M31

Это транзиентные ошибки Google Gemini API, произошедшие во время прогона v7. Текст ошибки:
```
503 UNAVAILABLE. {'error': {'code': 503, 'message': 'The service is currently unavailable.', 'status': 'UNAVAILABLE'}}
```

**Факты:**
- v6 (18 марта) — 0 ошибок API 503
- v7 (19 марта) — 3 ошибки API 503
- Модель: `gemini-3.1-flash-lite-preview` (одинаковая в обоих прогонах)

**Вывод**: Это НЕ связано с изменениями кода. Gemini API был нестабилен 19 марта. При повторном прогоне эти кейсы с высокой вероятностью отработают нормально.

**Рекомендация**: Добавить retry-логику (1-2 повторных попытки с exponential backoff) при 503/429/500 ошибках от Gemini API.

### Причина 2: Дефект fallback-логики для needs_input (4 кейса)

**Кейсы**: E15 (L4), M10, M27, M33 (L5)

#### Что должно было произойти

В рамках фикса P1/P2 была добавлена fallback-логика в `level5.py:77-88` и `level4.py:88-97`:

```python
# level5.py — новая fallback-логика
if result.missing_parameters:
    if result.selected_code_10 and result.selected_code_10.strip():
        # LLM picked a best-guess code — accept it
        result.confidence = min(result.confidence, 0.5)
        result.missing_parameters = []  # clear
    else:
        # LLM truly couldn't decide — propagate needs_input
        state.missing_parameters = result.missing_parameters
        ...
```

Промпт L5 был дополнен инструкцией:
> «ВСЕГДА заполняй selected_code_8 и selected_code_10 — даже если заполняешь missing_parameters.»

#### Что произошло на практике

Gemini `flash-lite` **НЕ следует** инструкции «всегда заполняй код». Когда модель решает запросить параметры, она:
1. Заполняет `missing_parameters` со списком параметров
2. Оставляет `selected_code_10` **пустой строкой** `""`
3. Fallback проверяет `if result.selected_code_10 and ...` → `""` is falsy → fallback **не срабатывает**
4. Каскад останавливается с needs_input

#### Доказательства

| Кейс | Остановка | v6 результат | v7 missing_parameters (язык!) |
|------|:---------:|:------------:|-------------------------------|
| E15 | L4 | 4412330000 ✅ | «толщина наружного слоя» (рус.) |
| M10 | L5 | 2204210800 ❌ | «PDO certification» (англ.) |
| M27 | L5 | 7307991000 ✅ | «quantitative breakdown» (англ.) |
| M33 | L5 | 8481808199 ✅ | «operating temperature range» (англ.) |

Обратите внимание: M27 и M33 отвечают **на английском** — это типичное поведение Gemini flash-lite, который иногда переключается на английский даже при русскоязычном промпте. Это отдельная проблема качества модели.

#### Почему в v6 эти кейсы работали?

В v6 промпт L5 был **проще и жёстче**:
> «Если карточка товара НЕ СОДЕРЖИТ параметра — ОСТАНОВИ КЛАССИФИКАЦИЮ и укажи missing_parameters.»

Парадоксально, эта жёсткая инструкция работала лучше, потому что модель чётко разделяла два пути:
- **Есть данные** → выбрать код (selected_code_10 заполнен)
- **Нет данных** → остановиться (selected_code_10 пуст)

В v7 промпт стал длиннее и сложнее (+20 строк с правилами вывода параметров, числовыми порогами и т.д.). Gemini flash-lite не справляется с таким количеством одновременных инструкций:
- Ищет числовые пороги → находит параметры, которые нужно проверить → решает запросить → но при этом не следует инструкции «всегда заполняй код»

**Ключевой вывод**: Для Gemini flash-lite **более простые промпты дают лучшие результаты**. Добавление детальных инструкций создаёт «парадокс сложности» — модель начинает сомневаться в большем количестве аспектов.

#### Рекомендация

1. **Исправить fallback-логику**: Не полагаться на LLM для заполнения кода при наличии missing_parameters. Вместо этого — **программно выбирать fallback-код** из доступных листьев:
   ```python
   if result.missing_parameters:
       if not result.selected_code_10 or not result.selected_code_10.strip():
           # LLM didn't pick a code — pick the "прочие" leaf programmatically
           result.selected_code_10 = leaves[-1].code  # последний = "прочие"
           result.selected_code_8 = result.selected_code_10[:8]
       result.confidence = min(result.confidence, 0.4)
       result.missing_parameters = []
   ```

2. **Упростить промпты для flash-lite**: Убрать детальные инструкции по выводу параметров. Оставить одно простое правило:
   > «Всегда выбирай код. Если не уверен — выбери наиболее общий ("прочие") и установи confidence < 0.5.»

3. **Или использовать более мощную модель для L5**: Gemini flash или Claude Haiku вместо flash-lite для L5 — модель, которая надёжнее следует сложным инструкциям.

### Причина 3: Загрузка примечаний (notes) увеличила контекст промптов

**Факт**: Между v6 и v7 были загружены 533 примечания в `tnved_notes`:
- 52 примечания к разделам
- 481 примечание к группам

**При v6**: таблица `tnved_notes` содержала **0 строк** — функция `seed_notes()` ещё не существовала в `seed_db.py`. Промпты L1/L2/L3 получали пустые списки примечаний.

**При v7**: все 533 примечаний загружены и передаются в промпты:
- L1 получает все 52 примечания к разделам
- L2 получает примечания к текущему разделу + ко всем группам раздела
- L3 получает примечания к текущей группе

Это значительно увеличивает длину промптов, что для Gemini flash-lite может снижать качество следования инструкциям. Однако напрямую доказать, что именно примечания вызвали конкретные регрессии, невозможно — ни один из регрессивных кейсов не имеет ошибку на уровне L1 (выбора раздела).

**Вывод**: Примечания — потенциальный фактор, но не основная причина. Они добавляют полезный контекст, но увеличивают нагрузку на модель.

### Причина 4: Нестабильность LLM (1 кейс)

**Кейс**: E10 (мрамор необработанный)

| | v6 | v7 |
|--|:--:|:--:|
| Heading | 2515 ✅ | 2515 ✅ |
| Subheading | 251511 ✅ | 251512 ❌ |
| Code 10 | 2515110000 ✅ | 2515120000 ❌ |

LLM выбрал 2515**12** (мрамор грубо раздробленный) вместо 2515**11** (мрамор необработанный). Описание товара: «мрамор необработанный, в блоках». Слово «блоки» однозначно указывает на 2515.11.

Эта ошибка — следствие нестабильности Gemini flash-lite (stochastic decoding). Промпт L4 для этого кейса не менялся существенным образом. При повторном запуске результат может быть как верным, так и неверным.

## Проверка P7 и P3

### P7: Галлюцинация кода 620193

```
v6: BENCH-H24 → error: "Subposition node not found: 620193"
v7: BENCH-H24 → error: "Subposition node not found: 620193"
```

Добавленная валидация в `level4.py:99-105` проверяет `result.selected_subposition not in valid_codes` и пытается найти closest match. Но фикс P7 в `level4.py` — это валидация **после** LLM-вызова. Для H24 LLM по-прежнему галлюцинирует код 620193, и валидация находит fallback-кандидата. Однако ошибка "node not found" в v7 говорит о том, что fallback-путь тоже не срабатывает — возможно, ошибка происходит в `level5.py` на следующем шаге, а не в `level4.py`.

### P3: Числовые пороги L4

Для BENCH-H18 (дрон 720 г → ≤250 г) и H19 (грузовик 8 т → ≤5 т):

```
v6: H18 → 8806210001 (≤250г) ❌  →  v7: H18 → 8806210001 (≤250г) ❌  (идентично!)
v6: H19 → 8704213200 (≤5т) ❌   →  v7: H19 → 8704213200 (≤5т) ❌   (идентично!)
```

Промпт L4 теперь содержит подробные инструкции по числовым порогам, но Gemini flash-lite их не соблюдает. Дрон с массой 720 г по-прежнему классифицируется как ≤250 г.

## Рекомендации для v8

### Критические (немедленные)

1. **Retry-логика для API-ошибок**: 1-2 повтора при 503/500/429. Это сразу «вернёт» 3 потерянных кейса.

2. **Программный fallback вместо LLM-fallback**: Если `missing_parameters` не пуст и `selected_code_10` пуст — программно выбрать последний (наиболее общий «прочие») код из доступных листьев, а не ждать от LLM заполнения обоих полей.

3. **Перепрогнать v7 для чистоты**: 3 ошибки API исказили результат. Нужен чистый прогон без транзиентных ошибок для реальной оценки эффекта P-фиксов.

### Среднесрочные

4. **Упростить промпты для flash-lite**: Вернуть более простые формулировки для L4/L5. Длинные инструкции с множеством правил перегружают flash-lite. Правило: для flash-lite — одна главная инструкция + 2-3 ключевых ограничения.

5. **Тестировать более мощные модели**: `gemini-3.1-flash` (без `-lite`) или `claude-haiku` для L3-L5. Текущий `gemini-3.1-flash-lite-preview` — самая слабая модель, она не справляется со сложными инструкциями.

6. **Фикс P7 для H24**: Ошибка «node not found: 620193» по-прежнему не исправлена. Нужно проверить, что валидация в `level4.py` действительно перехватывает галлюцинированный код и подставляет валидный.

### Стратегические

7. **Разделить «качество промптов» и «качество модели»**: Текущие промпты оптимизированы для более мощных моделей (Sonnet/Opus), но запускаются на flash-lite. Нужны отдельные наборы промптов для разных моделей или переход на более мощные модели.
