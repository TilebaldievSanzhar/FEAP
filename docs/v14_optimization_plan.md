## 2. Почему v10-v13 регрессировали (уроки прошлых итераций)

### v10: SGR v2 для L4/L5 → регрессия (-8pp code-10)
- **Что делали**: Добавили 6 SGR-полей в L4 (`hierarchy_parsing`, `product_card_parameter_check`, `parameter_extraction`, `threshold_analysis`, `selection_consistency_check`, `category_match` в кандидатах)
- **Почему регресс**: Flash-lite имеет жёсткий «бюджет внимания». Каждое доп. поле отнимает генеративную ёмкость у decision-полей. 6 аналитических полей — перебор.
- **Урок**: **Максимум 3-4 SGR-поля для flash-lite**. Каждое поле должно быть высокоценным.

### v10b: Откат tree_nodes.jinja2 → частичное восстановление
- **Что делали**: В v10 изменили shared `tree_nodes.jinja2` — добавили `{% if parent_category %}` — whitespace Jinja2 сломал рендеринг на ВСЕХ уровнях.
- **Урок**: **НИКОГДА не менять shared `tree_nodes.jinja2`**. Использовать per-level шаблоны.

### v11: Haiku на L4 → провал (heading=64%)
- **Что делали**: Anthropic Haiku 4.5 для L4 через per-level model override.
- **Почему регресс**: Anthropic tool_use ≠ Gemini constrained JSON. Совершенно другая механика structured output.
- **Урок**: **Оставаться в экосистеме Gemini** для constrained decoding.

### v12: Sonnet на L4 → ровно v9 (87/100 = v9's 87/100 без API-ошибок)
- **Что делали**: Anthropic Sonnet 4.6 для L4.
- **Результат**: ИДЕНТИЧНЫЙ v9. Более сильная модель дала ровно то же.
- **Урок**: **Bottleneck — не в модели, а в контексте**. Модель сильнее, но контекст тот же → результат тот же.

### v13: Context engineering → регрессия (-12pp code-10)
- **Что делали**: `[category] > detail` формат в tree_nodes_l4/l5, candidates в L5, удалили `product_card_parameter_check`.
- **Почему регресс**: `[brackets]` запутал flash-lite (интерпретировала как метаданные). L5 candidates перегрузили. Удаление grounding-поля ослабило.
- **Урок**: **Формат критичен**. Не использовать `[brackets]`. Не добавлять candidates-списки для flash-lite на L5.

## 4. Структурные проблемы кода (точные ссылки)

### 4.1 Порядок полей в SGR-схемах (критический дефект)

**Файл**: `src/feap/schemas/position.py:43-70`

Текущий порядок `PositionResult`:
```
section → group → step1_product_nature → step2_opi1_text_analysis → step3_ambiguity_resolution → candidates → selected_position
```

При constrained decoding Gemini генерирует поля **строго по порядку**. Модель пишет `step2_opi1_text_analysis` (анализ текстов позиций) **ДО** того, как сгенерировала `candidates`. Логический разрыв: анализирует то, что ещё не перечислила.

**Правильный порядок**: analysis → candidates → deeper_analysis → selection

Аналогичная проблема в:
- `src/feap/schemas/subposition.py:23-61` — `threshold_analysis` до `candidates`
- `src/feap/schemas/subsubposition.py:21-68` — `threshold_comparison` до `candidates`

### 4.2 Плоское дерево на L4

**Файл**: `src/feap/prompts/templates/context/tree_nodes_l4.jinja2`

Текущий формат (v13, с `[brackets]`):
```
- **850811** — [со встроенным электродвигателем] > мощностью не более 1500 Вт...
- **850870** — части
```

Проблемы:
1. `[brackets]` воспринимается flash-lite как метаданные, а не как название ветки
2. Плоский список — модель не видит, что 850811/850819 = одна ветка, а 850870 = другая
3. Слово «прочие» появляется на разных уровнях иерархии — неоднозначность

**Файл**: `src/feap/prompts/templates/context/tree_nodes.jinja2` — generic шаблон (4 строки, работает стабильно на L1-L3, НЕ МЕНЯТЬ)

### 4.3 Decision chain — избыточность

**Файл**: `src/feap/prompts/templates/context/decision_chain.jinja2`

Полная цепочка с reasoning, rules, confidence передаётся на КАЖДЫЙ уровень. На L4 для выбора субпозиции нужен только код позиции (4 цифры) — остальные ~500-800 токенов бесполезны.

### 4.4 SGR-поля L4 — текущее состояние

**Файл**: `src/feap/schemas/subposition.py:23-61`

Текущие SGR-поля (4 штуки):
1. `hierarchy_parsing` — «разбор дерева по категориям» (слишком размытая инструкция)
2. `parameter_extraction` — цитирование параметров из карточки
3. `threshold_analysis` — сопоставление с порогами
4. `selection_consistency_check` — проверка ПОСЛЕ выбора (бесполезна для constrained decoding)

**Проблема**: ни одно поле не заставляет модель ЯВНО утвердить тип товара («целое устройство» vs «часть») и ЯВНО выбрать ветку дерева.

### 4.5 Промпт L4 — раздут примерами

**Файл**: `src/feap/prompts/templates/system/level4_subposition.jinja2` (54 строки)

Содержит конкретные примеры ошибок (МФУ, робот-пылесос, кухонная мебель) — добавлены в v13. Это правильно, но примеры занимают ~200 токенов system prompt. Нужно оптимизировать.

## 5. Инсайты из SGR-источников (abdullin.com)

### 5.1 Три паттерна SGR

| Паттерн | Суть | Когда применять |
|---|---|---|
| **Cascade** | Последовательные шаги от общего к конкретному | Оценка, анализ, принятие решений |
| **Routing** | Явный выбор ветки через Union/Literal, затем branch-specific анализ | Классификация, маршрутизация, tool selection |
| **Cycle** | Повторение шага N раз (List с min/max bounds) | Перечисление кандидатов, рисков, факторов |

**Текущее**: L4 использует Cascade (analyse → decide).
**Нужное**: L4 — это **Routing** (выбери ветку → анализируй внутри ветки → выбери код).

### 5.2 Ключевые принципы

1. **Имена полей = семантические инструкции**. `product_type_assertion` более директивно, чем `hierarchy_parsing`.
2. **«Throwaway» поля**: поля, которые модель заполняет для направления мышления, но не используются в бизнес-логике. Наш подход SGR уже это делает.
3. **Порядок полей = бюджет мышления**: ранние поля дают модели «пространство подумать» до финального выбора.
4. **Слабые модели выигрывают больше**: SGR даёт +5-10% для слабых моделей (наш случай).
5. **Держать схемы фокусированными**: одна схема = одна задача рассуждения. Не пихать всё в одну гигантскую схему.

### 5.3 Выводы для L4

Из паттерна Routing: вместо свободного анализа, модель должна **сначала сделать routing decision** (выбрать ветку дерева), а потом анализировать внутри ветки.

Из text-to-SQL примера: одно поле `strategy` перед `sql_query` дало +6% accuracy. Аналогично, поле `branch_selection` перед `candidates` может дать аналогичный эффект.

#### 1.2 Новые SGR-поля L4 — Routing pattern

**Файл**: `src/feap/schemas/subposition.py`

Текущие поля (4): `hierarchy_parsing`, `parameter_extraction`, `threshold_analysis`, `selection_consistency_check`

Новые поля (3, МЕНЬШЕ текущего):
```python
class SubpositionResult(BaseModel):
    position: str
    # --- SGR Step 1: Routing (выбор ветки) ---
    product_type_assertion: str = Field(

        "Назови ветку и объясни почему. НЕ ВЫБИРАЙ ветку 'части' для целого устройства."
    )
    # --- SGR Step 2: Параметры + пороги (объединение) ---

    # --- Решение ---
    candidates: list[SubpositionCandidate]
    selected_subposition: str
    applied_rules: list[str]

    missing_parameters: list[str]
```

Ключевые изменения:
- **3 поля вместо 4** (меньше нагрузка на flash-lite)
- **`product_type_assertion`** — явное утверждение типа товара (предотвращает «части vs целое»)
- **`branch_selection`** — явный routing step (предотвращает «прочие vs конкретная ветка»)
- **`parameter_threshold_match`** — объединение extraction + analysis в одно поле
- **Убран `selection_consistency_check`** — post-hoc проверка бесполезна для flash-lite
- **`candidates` ПЕРЕД `selected_subposition`** — правильный порядок для constrained decoding

### Фаза 2: «Доменный контекст» (85% → 88-90%)

**Цель**: Решить ошибки категории B через доменные знания в контексте.

#### 2.1 Few-shot примеры в L4 промпте

Добавить **краткие** примеры для частых ошибочных паттернов (по ~30 токенов каждый):

```
ПРИМЕРЫ КЛАССИФИКАЦИИ:
• Портативная Bluetooth-колонка с несколькими динамиками → 851821 (одиночный, НЕ 851822 комплект)
• МФУ (печать+копия+скан) → ветка «принтеры» (8443.3x), НЕ «прочие» (8443.99)
• Мебель в разобранном виде (ОПИ 2а) → целая мебель, НЕ «части»
• Восстановленный сок из концентрата → Brix обычно 40-60 (>20)
```

~120 токенов — окупается устранением 4+ ошибок.

#### 2.2 Субпозиционные пояснения

Текущий `get_explanations_for_position()` загружает пояснения к ПОЗИЦИИ. Но пояснения к позициям часто содержат секции, описывающие конкретные субпозиции (обозначенные буквами А, Б, В или нумерацией).

**Предложение**: Парсить субпозиционные секции из пояснений и подгружать ТОЛЬКО релевантные.

Сложность: средняя (нужен парсер секций пояснений). Отложить до подтверждения эффекта Фазы 1.

### Фаза 3: «Самокоррекция» (90% → 93-95%)

**Цель**: Устранить остаточные стохастические ошибки.

#### 3.1 Confidence-based retry для L4

**Файл**: `src/feap/cascade/levels/level4.py`

```python
result = await classify(level=4, ...)
if result.confidence < 0.6:
    # Формируем hint из первой попытки
    retry_context = (
        f"Первая попытка выбрала {result.selected_subposition} "
        f"(confidence={result.confidence:.1f}). Перепроверь."
    )
    result2 = await classify(level=4, user_message=user + "\n\n" + retry_context, ...)
    if result2.confidence > result.confidence:
        result = result2
```

Стоимость: ~+20% средняя (retry на ~30% кейсов).
Ожидаемый эффект: +3-5pp code-10 за счёт устранения стохастических low-confidence ошибок.

#### 3.2 Аудит ground truth

Проверить потенциальные ошибки бенчмарка:
- **E30**: 970121 = «возрастом >100 лет» (БД) vs notes «менее 100 лет». Картина 2024г → 970191 правильно?
- **H02**: 844331 (2+ функции + сеть) vs 844332 (1 функция + сеть). МФУ с 4 функциями → 844331?

## 12. Философия подхода

Предыдущие итерации (v10-v13) действовали по принципу «добавить больше» — больше полей, больше контекста, больше примеров. Каждый раз это перегружало flash-lite и вызывало регресс.

v14 действует по принципу **«заменить на лучшее»**:
- Не добавлять поля, а **заменить** размытые на точные (hierarchy_parsing → product_type_assertion + branch_selection)
- Не добавлять контекст, а **реструктурировать** (плоский список → группированные ветки)
- Не увеличивать количество, а **повысить плотность** информации (compact chain, targeted few-shots)

SGR работает не потому что полей много, а потому что **каждое поле направляет мышление модели в нужном направлении**. Три точных поля > шести размытых.
