## 1. Проблема

### 1.1 Стартовая точка (v21, SGR Qualifier Check)

| Уровень | Точность |
|---------|----------|
| Heading (4-digit) | 97.0% |
| Subheading (6-digit) | 88.0% |
| Code-8 | 77.0% |
| Code-10 | 74.0% |

Bottleneck — L4/L5 (subheading → code-10). Цель — пробить 75%+ code-10.

### 1.2 Контекст: SGR работает

Первоначальное внедрение SGR (до v16) дало **ощутимый прирост** — аналитические поля перед решением направляют reasoning модели. Инструмент доказал эффективность.

Проблема — в последующих **оптимизациях**: каждая попытка "улучшить" SGR давала регрессию.

## 2. Эксперименты и результаты

### 2.1 Хронология

| Версия | Подход | Sub. | C8 | C10 | Δ от v21 |
|:------:|--------|:----:|:--:|:---:|:--------:|
| v16* | Рабочий SGR (parameter_extraction + threshold) | 91% | 81% | **77%** | +3% |
| v21 | SGR + qualifier_check + category_match + dash_level_check | 88% | 77% | 74% | baseline |
| v22 | **DTN** (3 навигационных поля, qualifier убран) | 85% | 71% | 69% | -5% |
| v23 | **DTN + Verify** (4-й шаг верификации) | 74% | 62% | 59% | **-15%** |
| v24 | **Возврат к рабочему SGR** + specificity_check | ?% | ?% | ?% | ? |

*v16 — лучший результат, точная конфигурация не сохранена в git, но известно что использовал оригинальные SGR-поля.

### 2.2 Анализ: что работает, а что ломает

**РАБОТАЕТ — поля про предмет (факты):**
- `parameter_extraction` — "Какие параметры у товара?"
- `threshold_analysis` — "Есть пороги? Сравни."
- `relevant_parameters` — "Что влияет на выбор?"
- `code_differentiation` — "Чем различаются коды?"

Эти поля **направляют** reasoning, не **заменяя** его. Модель извлекает факты, сравнивает, и САМА делает вывод.

**ЛОМАЕТ — поля про процесс (инструкции):**
- `qualifier_check` ×N кандидатов — параллельная оценка, overload attention
- `category_match` (direct/residual) — жёсткая категоризация, ограничивает свободу модели
- `step1_tree_structure` / `step3_navigation` — абстрактные мета-концепции ("развилки")
- `step4_verify` — confirmation bias, невозможность "вернуться" при constrained decoding
- `dash_level_check` — структурная проверка, не нужная если контекст правильно отображает иерархию

**Принцип**: SGR-поля должны спрашивать "ЧТО?" (факты о товаре и кодах), а не "КАК?" (процедура принятия решения).

### 2.3 Почему DTN провалился

DTN заменил предметные поля **процедурными**: "определи критерий → найди значение → пройди по дереву". Это:
1. **Абстрактно** — "развилка" это мета-концепция, light-модель не привыкла так думать
2. **Процедурно** — модель следует инструкции вместо того чтобы рассуждать
3. **Без safety net** — убраны ВСЕ предметные поля, модель теряет "якоря" для reasoning

### 2.4 Почему Verify ухудшил ещё больше

- При constrained decoding модель не может изменить предыдущие поля → "вернись и выбери другой" невозможно
- Инструкция "подтверди или вернись" создаёт **конфликт** → модель дезориентирована
- Confirmation bias: модель рационализирует свой же выбор вместо проверки

## 3. Решение v24: возврат к рабочей формуле + одно дополнение

### 3.1 Принцип

Вернуть **оригинальные предметные SGR-поля** (как в v16) + добавить **один** directed reasoning step (`specificity_check`), который адресует самый частый тип ошибки (6 из 26 в v21 — "прочие" vs конкретный код).

### 3.2 L4 — SubpositionResult

| Поле | Тип | Описание |
|------|-----|----------|
| `parameter_extraction` | Факт | Какие характеристики товара влияют на выбор? |
| `threshold_analysis` | Факт | Есть числовые пороги? Сопоставь. |
| `specificity_check` | Reasoning | Есть ли код, КОНКРЕТНО описывающий товар, или «прочие»? |
| `candidates` | Решение | 2-5 кандидатов |
| `selected_subposition` | Решение | Выбор |

**3 поля** (2 факта + 1 reasoning) vs 6-7 в v21 или 3-4 процедурных в v22/v23.

### 3.3 L5a — SubsubpositionShortlistResult (8-digit branch)

| Поле | Тип | Описание |
|------|-----|----------|
| `relevant_parameters` | Факт | Какие параметры влияют на выбор ветки? |
| `code_differentiation` | Факт | Чем различаются ветки? |
| `candidates` → `selected_code_8` | Решение | |

**2 поля** — без threshold (пороги редки на уровне веток).

### 3.4 L5b — SubsubpositionResult (10-digit code)

| Поле | Тип | Описание |
|------|-----|----------|
| `relevant_parameters` | Факт | Какие параметры влияют? |
| `code_differentiation` | Факт | Чем различаются коды? |
| `threshold_comparison` | Факт | Сопоставление с порогами |
| `candidates` → `selected_code_10` | Решение | |

**3 поля** — все предметные, как в оригинальном SGR.

### 3.5 Промпты

Минимальные, без методологических директив:

```
ЗАДАЧА: Определить субпозицию (6-значный код) внутри позиции XXXX.

ПОРЯДОК АНАЛИЗА (заполняй поля по порядку):
1. parameter_extraction — перечисли характеристики товара...
2. threshold_analysis — если есть числовые пороги, сопоставь...
3. specificity_check — есть ли код, который конкретно называет товар?
4. candidates — заполни кандидатов.
5. selected_subposition — выбери.

ПРАВИЛА:
- Код ДОЛЖЕН быть из списка.
- «не более X» = включительно.
```

~15 строк. Без "МЕТОД:", без "⚠️ КРИТИЧЕСКИЙ ШАГ", без "НАВИГАЦИЯ ПО ДЕРЕВУ".

### 3.6 Контекстные шаблоны

Оставлен формат с `[ВЕТКАМИ]` из DTN — это просто визуальное улучшение рендеринга иерархии, не влияющее на SGR-подход.

## 7. Ключевые уроки

1. **SGR = направление, не замена** reasoning. Поля должны спрашивать "что?" (факты), а не "как?" (процедура).
2. **Меньше полей = лучше** для light-моделей. 2-3 предметных поля > 6-7 процедурных.
3. **Свобода модели** — модель рассуждает лучше, когда ей дают факты и свободу, а не пошаговую инструкцию.
4. **Constrained decoding ≠ backtracking** — инструкции "вернись" невозможны при последовательной генерации.
5. **Confirmation bias** — просить модель "проверить свой выбор" в том же вызове не работает.
