# Пояснения к ТН ВЭД: RAG vs прямая загрузка — глубокий анализ

## 1. Постановка проблемы

На уровнях L3 (позиция, 4 цифры) и L4 (субпозиция, 6 цифр) каскада LLM должен получить **пояснения** — юридический текст ЕЭК, который объясняет, что включается и что исключается из каждого кода. Это ключевой контекст для точной классификации.

Пояснения — это ~97 PDF-файлов (по одному на группу ТН ВЭД), скачиваемых с сайта ЕЭК (`psn01.pdf` – `psn97.pdf`). Каждый файл содержит от 10 до 200+ страниц сплошного текста с определённой, но не машиночитаемой структурой.

**Ключевой вопрос:** как доставить пояснения в контекст LLM — через RAG (семантический поиск по эмбеддингам) или через прямую загрузку из БД по коду?

---

## 2. Два подхода

### Путь A — RAG (текущая реализация)

```
PDF → PyMuPDF → split по позициям (regex) → chunk_text (1200 токенов, overlap 150)
  → Voyage AI embed_documents() → pgvector
  → На L3/L4: embed_query(описание товара) → cosine similarity → top-k чанков в контекст
```

Файлы: `scripts/parse_explanatory_pdfs.py`, `scripts/generate_embeddings.py`, `src/feap/rag/retriever.py`, `src/feap/rag/embedder.py`.

### Путь B — Прямая загрузка (предлагаемый)

```
PDF → PyMuPDF → split по позициям → split по секциям (general / includes / excludes)
  → PostgreSQL (code + section_type + content)
  → На L3/L4: SELECT WHERE code IN (...) → полный текст секций в контекст
```

---

## 3. Почему RAG для пояснений — неправильный инструмент

### 3.1. Мы уже знаем коды — семантический поиск избыточен

На момент вызова L3b у нас есть shortlist из 2–5 кандидатов (конкретные 4-значные коды). На L4 — один конкретный код позиции. Задача — загрузить пояснения **именно к этим кодам**, а не искать «семантически похожие» чанки.

RAG решает задачу: «найди релевантные документы, когда ты не знаешь, где искать». Но мы знаем точно — нам нужен текст пояснения к позиции 8509, а не «что-то похожее на электрическую зубную щётку».

### 3.2. Чанкинг уничтожает структуру пояснений

Текущий парсер (`parse_explanatory_pdfs.py`) разбивает текст каждой позиции на чанки по ~1200 токенов с overlap 150. При этом:

- **Пояснение к позиции — это единый юридический документ.** Оно содержит определение, перечень включений, перечень исключений (с перенаправлениями на другие коды), примеры. Всё это логически связано.
- **Чанкинг рвёт эту связность.** «В данную позицию не включаются:» может оказаться в конце одного чанка, а список исключений — в начале следующего. LLM получает обрывки вместо полного юридического контекста.
- **Overlap (150 токенов) не решает проблему.** Он дублирует фрагменты текста, увеличивая объём, но не восстанавливает логическую целостность.

### 3.3. Embedding drift — разные семантические пространства

Описание товара от пользователя и юридический текст пояснений — это разные «языки»:

| Пользователь | Пояснение ЕЭК |
|---|---|
| «электрическая зубная щётка Oral-B» | «Машины электромеханические бытовые со встроенным электродвигателем, кроме пылесосов товарной позиции 8508» |
| «кожаная сумка женская» | «Изделия из натуральной кожи или композиционной кожи... за исключением предметов, упомянутых в примечании 2 к данной группе» |

Cosine similarity между этими текстами может быть неожиданно низким. Эмбеддинг «электрическая зубная щётка» может оказаться ближе к чанку про электробритвы (8510), чем к нужному чанку про позицию 8509.

### 3.4. Top-k может пропустить критичную информацию

При `limit=5` чанков модель видит 5 наиболее «похожих» фрагментов. Но:

- Исключающее примечание («В данную позицию **не** включаются...») семантически непохоже на описание товара — оно описывает, чем товар **не является**
- Определение термина, критичное для классификации, может быть в чанке с низким cosine similarity
- Прямая загрузка по коду гарантирует: всё, что относится к позиции — будет в контексте

### 3.5. Лишняя задержка и стоимость

Каждый вызов L3/L4:
- HTTP-запрос к Voyage AI для embed_query: **300–500 мс** + стоимость API
- pgvector cosine distance search: **~10 мс**
- Итого: **~0.5 сек** дополнительной задержки на уровень

Прямой `SELECT WHERE code IN (...)`: **~1–5 мс**. Разница в 100x.

## 4. Объёмы контекста при прямой загрузке

### 4.1. Типичные объёмы

| Уровень | Что загружаем | SQL-фильтр | Типичный объём | Токены (рус.) |
|---------|--------------|------------|---------------|---------------|
| L3a (shortlist) | Ничего — пояснения не нужны | — | — | — |
| L3b (deep analysis) | Пояснения к 2–5 кандидатам | `code IN ('8509', '8516', '8510')` | 5–50 KB | 2–20K |
| L4 (субпозиция) | Пояснения к 1 позиции | `code = '8509'` | 2–20 KB | 1–8K |

### 4.2. Worst case — большие пояснения

Некоторые позиции имеют огромные пояснения:

| Позиция | Описание | Ожидаемый объём |
|---------|----------|----------------|
| 8471 | Вычислительные машины | ~60 KB ≈ 25K токенов |
| 8443 | Печатное оборудование | ~40 KB ≈ 16K токенов |
| 3004 | Лекарственные средства | ~50 KB ≈ 20K токенов |

Worst case L3b: 5 кандидатов × 25K = 125K токенов. Это **технически допустимо** (Claude Sonnet/Opus: 200K контекст), но дорого.

### 4.3. Влияет ли большой контекст на точность?

**Скорее нет**, по нескольким причинам:

1. Claude хорошо работает с длинным структурированным контекстом (это его сильная сторона)
2. Системный промпт явно направляет: «изучи пояснения к кандидатам и определи позицию» — LLM знает, зачем ему дан этот текст
3. Пояснения — это именно тот материал, который LLM **должен прочитать целиком**, а не обрывками
4. Структурирование по секциям (general / includes / excludes) помогает навигации

**Реальный риск — стоимость**, а не точность. Mitigation:
- Anthropic prompt caching (бета) — закэшировать системный промпт + ОПИ
- На L3b использовать Sonnet вместо Opus для экономии (с fallback на Opus при низком confidence)

## 5. Структура хранения пояснений (целевая)

### 5.1. Схема таблицы

```sql
-- Переработанная таблица explanatory_notes
-- Каждая запись = одна логическая секция пояснения к одной позиции
-- НЕ чанки, а полные смысловые блоки

CREATE TABLE tnved_explanatory_notes (
    id SERIAL PRIMARY KEY,
    code VARCHAR(10) NOT NULL,           -- '8509' для позиции, '85' для общих положений группы
    group_code VARCHAR(2) NOT NULL,      -- '85' — для фильтрации
    code_level INTEGER NOT NULL,         -- 1=группа (общие положения), 2=позиция
    section_type VARCHAR(20) NOT NULL,   -- 'general' | 'includes' | 'excludes'
    title TEXT,                          -- заголовок секции (если есть)
    content TEXT NOT NULL,               -- ПОЛНЫЙ текст секции
    content_tokens INTEGER,              -- примерное количество токенов (для бюджетирования)
    source_file VARCHAR(100),            -- 'psn85.pdf'
    page_number INTEGER,                 -- начальная страница в PDF (для аудита)
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_expl_code ON tnved_explanatory_notes(code);
CREATE INDEX idx_expl_group ON tnved_explanatory_notes(group_code);
CREATE INDEX idx_expl_level ON tnved_explanatory_notes(code_level);
```

### 5.2. Примеры записей

```
code='85',   section_type='general',  content='Общие положения к группе 85...'
code='8509', section_type='general',  content='Машины электромеханические бытовые...'
code='8509', section_type='includes', content='В данную позицию включаются: 1) ...'
code='8509', section_type='excludes', content='В данную позицию не включаются: а) ...'
```

1–4 записи на позицию (вместо N чанков). ~1200–1500 позиций в ТН ВЭД → ~3000–5000 записей в таблице.

### 5.3. Запросы

```python
# L3b: пояснения к кандидатам
async def get_explanations_by_codes(session, codes: list[str]) -> list[ExplanatoryNote]:
    return (await session.execute(
        select(ExplanatoryNote)
        .where(ExplanatoryNote.code.in_(codes))
        .order_by(ExplanatoryNote.code, ExplanatoryNote.section_type)
    )).scalars().all()

# L4: пояснения к одной позиции
async def get_explanations_for_position(session, code: str) -> list[ExplanatoryNote]:
    return (await session.execute(
        select(ExplanatoryNote)
        .where(ExplanatoryNote.code == code)
        .order_by(ExplanatoryNote.section_type)
    )).scalars().all()
```

## 6. Парсинг PDF — детальная стратегия

### 6.1. Текущий парсер и его проблемы

Текущий `scripts/parse_explanatory_pdfs.py` делает:

1. **Извлечение текста** — `PyMuPDF (fitz) → page.get_text()` — OK
2. **Split по позициям** — regex `^\d{2}\.\d{2}\b` — OK, но есть нюансы
3. **Classify section** — ищет маркеры «включаются/не включаются» в первых 500 символах — **грубо**, одна позиция получает один `section_type`
4. **Chunk text** — разбивка на чанки по 1200 токенов с overlap — **не нужна** при прямой загрузке

Главная проблема: шаг 3 присваивает один `section_type` всей позиции целиком. Но позиция обычно содержит ВСЕ три типа секций: general + includes + excludes. Нужно разбивать позицию на секции.

### 6.2. Структура пояснения в PDF (реальная)

Типичная структура текста после извлечения из PDF:

```
ГРУППА 85

Электрические машины и оборудование, их части; звукозаписывающая и
звуковоспроизводящая аппаратура, аппаратура для записи и воспроизведения
телевизионного изображения и звука...

[Общие положения к группе — несколько абзацев или страниц]

85.01  Электродвигатели и электрогенераторы (кроме электрогенераторных установок).

      Двигатели и генераторы данной позиции представляют собой машины,
      преобразующие...
      [Общий текст пояснения — может быть от 1 абзаца до нескольких страниц]

      (А) ЭЛЕКТРОДВИГАТЕЛИ
         [Пояснительный текст подсекции A]

      (Б) ЭЛЕКТРОГЕНЕРАТОРЫ
         [Пояснительный текст подсекции Б]

      В данную позицию включаются:
        1) Двигатели постоянного тока мощностью...
        2) Двигатели переменного тока...
        3) ...

      В данную позицию не включаются:
        а) Электрогенераторные установки (товарная позиция 85.02)
        б) Электромагниты (товарная позиция 85.05)
        в) ...

85.02  Электрогенераторные установки и вращающиеся электрические преобразователи.
      ...
```

### 6.3. Сложности при парсинге

#### Проблема 1: Шум от PyMuPDF

`page.get_text()` извлекает весь текст страницы, включая:
- Колонтитулы (номера страниц, заголовки разделов повторяющиеся на каждой странице)
- Артефакты форматирования (разрыв слова при переносе строки)
- Таблицы, которые превращаются в беспорядочные строки текста
- Примечания сносок, вклинивающиеся в основной текст

**Решение:** пост-обработка — удаление повторяющихся заголовков, склейка разорванных слов (`-\n` → `\n` не всегда корректно, нужна аккуратность с дефисами в русском тексте).

#### Проблема 2: Вариативность маркеров

Маркеры включений/исключений не унифицированы по всем 97 файлам. Встречаются варианты:

```
В данную позицию включаются:
В данную товарную позицию включаются:
В данную позицию также включаются:
В данную субпозицию включаются:
В данную группу включаются:
Сюда включаются:
Сюда также включаются:
К данной категории относятся:
включаются также:
```

Аналогично для исключений:

```
В данную позицию не включаются:
В данную товарную позицию не включаются:
В данную позицию не входят:
Не включаются:
Сюда не включаются:
```

**Решение:** расширенные regex-паттерны с перечислением всех встреченных вариантов. Или двухпроходная стратегия: первый проход — собрать все встреченные маркеры по 97 файлам, второй — написать финальные regex.

#### Проблема 3: Подсекции внутри позиции

Некоторые позиции содержат подсекции, обозначенные буквами или римскими цифрами:

```
(А) ЭЛЕКТРОДВИГАТЕЛИ
(Б) ЭЛЕКТРОГЕНЕРАТОРЫ
(I) Двигатели постоянного тока
(II) Двигатели переменного тока
1° Синхронные двигатели
2° Асинхронные двигатели
```

Каждая подсекция может иметь свои собственные блоки включений/исключений. Это создаёт вложенную структуру, которую нужно либо разворачивать в плоский список секций, либо хранить как единый блок `general`.

**Решение (прагматичное):** не пытаться парсить подсекции. Хранить как части `general`-блока позиции. Маркеры «включаются/не включаются» отделять независимо от вложенности.

#### Проблема 4: Позиции с пояснениями к субпозициям

В некоторых PDF есть пояснения не только к 4-значным позициям, но и к 6-значным субпозициям:

```
8471.30  Вычислительные машины портативные массой не более 10 кг...
    [Пояснение к субпозиции]
```

Заголовок субпозиции: `\d{4}\.\d{2}` (четыре цифры, точка, две цифры).

**Решение:** расширить regex для разбивки, добавив паттерн субпозиций. Хранить с `code_level=3` (субпозиция). На L4 загружать вместе с пояснениями к позиции.

#### Проблема 5: Ссылки в исключениях

Исключения часто содержат перенаправления:

```
В данную позицию не включаются:
  а) Электрогенераторные установки (товарная позиция 85.02)
  б) Стартёры (товарная позиция 85.11)
```

Полезно извлечь коды-ссылки (`8502`, `8511`) в отдельное поле `references_to`. Это может пригодиться для автоматической проверки backtracking.

**Решение:** regex для извлечения кодов из скобок: `\((?:товарная позиция|товарные позиции|группа|позиция)\s+(\d{2}\.\d{2})\)` — и сохранение в массив `references_to`.

### 6.4. Предлагаемый алгоритм парсинга (переработанный)

```
Шаг 1: Извлечение текста
  → PyMuPDF page.get_text() для каждого PDF
  → Очистка: удаление колонтитулов, склейка переносов

Шаг 2: Разбивка по позициям
  → Regex: ^(\d{2})\.(\d{2})\b — для 4-значных позиций
  → Regex: ^(\d{4})\.(\d{2})\b — для 6-значных субпозиций (опционально)
  → Текст до первой позиции → general_notes группы (code = group_code)

Шаг 3: Разбивка каждой позиции на секции
  Для каждой позиции пройти по тексту и выделить блоки:

  а) Найти маркер EXCLUDES — от него до конца или до следующего маркера → секция 'excludes'
  б) Найти маркер INCLUDES — от него до EXCLUDES или до конца → секция 'includes'
  в) Всё ДО первого маркера (или весь текст, если маркеров нет) → секция 'general'

  Порядок поиска: EXCLUDES → INCLUDES → остаток = GENERAL
  (ищем сначала excludes, потому что "не включаются" может идти после "включаются")

  Если маркеров несколько (например, два блока "включаются"):
  → объединить в одну секцию или создать отдельные записи с суффиксами

Шаг 4: Извлечение ссылок из excludes
  → Regex для кодов в скобках → массив references_to

Шаг 5: Подсчёт токенов
  → len(content) / 4 (грубая оценка для русского текста)
  → Сохранить в content_tokens для бюджетирования контекста

Шаг 6: Сохранение
  → JSON для промежуточного хранения (data/parsed/explanatory_notes.json)
  → Прямая загрузка в БД через seed_db.py
```

### 6.5. Обработка edge cases при парсинге

| Ситуация | Решение |
|----------|---------|
| Позиция без маркеров includes/excludes | Весь текст → одна запись `section_type='general'` |
| Несколько блоков «включаются» в одной позиции | Объединить в один `includes` |
| Маркер «также включаются» после «не включаются» | Отнести к `includes`, обрабатывать по порядку появления |
| Пояснение к субпозиции (6-значный код) | Отдельная запись с `code_level=3` |
| Пустой или очень короткий текст (<50 символов) | Пропустить, не создавать запись |
| PDF не содержит позиций (только общие положения) | Одна запись с `code=group_code`, `section_type='general'` |
| Таблицы в PDF (например, технические характеристики) | PyMuPDF `page.get_text("dict")` для лучшего извлечения, или оставить как есть |

## 8. Сравнение подходов — итоговая таблица

| Критерий | RAG (текущий) | Прямая загрузка (предлагаемый) |
|----------|---------------|-------------------------------|
| **Точность контекста** | Top-k чанков, возможен пропуск критичных | Гарантированно ВСЕ данные по коду |
| **Целостность текста** | Рваные чанки (1200 токенов) | Полные секции (general/includes/excludes) |
| **Задержка** | ~500 мс (Voyage API + pgvector) | ~1–5 мс (SQL по индексу) |
| **Стоимость** | Voyage API за каждый запрос + хранение эмбеддингов | Только PostgreSQL |
| **Зависимости** | Voyage AI API (внешний сервис) | Нет внешних зависимостей |
| **Сложность парсинга** | Низкая (chunk_text — механическая нарезка) | Средняя (нужны regex для секций) |
| **Объём контекста** | Предсказуемый (top-k × chunk_size) | Переменный (зависит от позиции, 2–25K токенов) |
| **Подготовка данных** | Парсинг + эмбеддинги (~часы на 97 файлов) | Только парсинг (~минуты) |
| **Offline-работа** | Невозможна (нужен Voyage API) | Полностью автономна |

---

## 9. Бюджетирование контекста на L3b

На L3b в контекст LLM попадают:

| Компонент | Токены |
|-----------|--------|
| Системный промпт (role + L3 deep instructions + ОПИ 1–5) | ~2–3K |
| Карточка товара | ~0.5–1K |
| Цепочка решений (L1 + L2) | ~0.3K |
| Примечания к группе | ~2–5K |
| **Пояснения к 2–5 кандидатам** | **2–20K (типично 5–10K)** |
| Итого входных | ~8–30K |
| Max output (reasoning + JSON) | ~4K |

При контексте Claude 200K — запас более чем достаточный даже для worst case.

Если когда-либо потребуется уменьшить контекст (например, для более дешёвой модели), возможные стратегии:
1. Загрузить только `excludes` + `general` (без `includes`) — обычно excludes критичнее
2. Ограничить кандидатов до 2–3 вместо 5
3. Truncate пояснений длиннее N токенов (с предупреждением в промпте)
