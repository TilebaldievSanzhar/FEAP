## 5. Стоимость за ПРАВИЛЬНУЮ классификацию

Чистая стоимость за запрос не отражает реальную экономику. Важна **стоимость за правильный результат**:

### По heading (4-digit)

| Модель | $/запрос | Accuracy | **$/правильный heading** |
|--------|:--------:|:--------:|:------------------------:|
| flash-lite (v6) | $0.015 | 80% | **$0.019** |
| **2.5-flash (v8)** | **$0.033** | **94%** | **$0.035** |

### По code-10 (10-digit)

| Модель | $/запрос | Accuracy | **$/правильный code-10** |
|--------|:--------:|:--------:|:------------------------:|
| flash-lite (v6) | $0.015 | 62% | **$0.024** |
| **2.5-flash (v8)** | **$0.033** | **73%** | **$0.045** |

**Вывод**: gemini-2.5-flash стоит **~1.8-1.9x дороже за правильный результат**. Прирост качества (+14 heading, +11 code-10) обходится в 2x.

### Скрытая экономия v8

Но есть факторы, которые таблица не учитывает:

1. **Ноль ложных needs_input**: v6 выдавала 15% запросов как needs_input → пользователь должен был отвечать на вопросы и перезапускать → x2 стоимость для 15% кейсов
2. **Меньше ручной проверки**: 94% accuracy = меньше обращений к экспертам
3. **Нет API 503 ошибок**: v7 имела 3-4 ошибки API → повторные запросы

С учётом этого реальный множитель ближе к **~1.5x**, а не 1.9x.

## 9. Возможности дальнейшей оптимизации

### 9.1. Уменьшить thinkingBudget (потенциал: -20-30% стоимости)

Текущий `thinkingBudget=1024` → ~$0.016 за thinking (48% стоимости). Варианты:

| thinkingBudget | Thinking tok | Thinking cost | Total cost | vs текущая |
|:--------------:|:------------:|:-------------:|:----------:|:----------:|
| 1024 (текущий) | ~6,400 | $0.016 | $0.033 | baseline |
| 512 | ~3,200 | $0.008 | $0.025 | **-24%** |
| 256 | ~1,600 | $0.004 | $0.021 | **-36%** |
| 0 (без thinking) | 0 | $0 | $0.017 | **-48%** |

**Риск**: Уменьшение thinking может снизить accuracy. Нужен бенчмарк с разными значениями.

### 9.2. Гибрид: flash-lite + flash (потенциал: -50% стоимости)

Идея: использовать дешёвую gemini-2.5-flash-lite ($0.10/$0.40) для простых уровней, а gemini-2.5-flash только там, где thinking критичен.

| Уровень | Модель | Обоснование |
|---------|--------|-------------|
| L0 | flash-lite | Обогащение — простая задача |
| L1a | flash-lite | Shortlist из 21 раздела — тривиально |
| L1b | flash-lite | Проверка 2-3 кандидатов — простая |
| L2 | flash-lite | Выбор группы — обычно очевидно |
| **L3a** | **flash-lite** | Shortlist позиций — умеренная сложность |
| **L3b** | **2.5-flash** | Глубокий анализ с ОПИ — **нужен thinking** |
| L4 | flash-lite или 2.5-flash | Зависит от сложности |
| L5 | flash-lite | Финальный код — если параметры известны, тривиально |

**Оценка стоимости гибрида:**

```
flash-lite levels (L0, L1a, L1b, L2, L3a, L5):
  Input:  ~24,290 tok × $0.10/MTok = $0.0024
  Output: ~1,700 tok  × $0.40/MTok = $0.0007

2.5-flash levels (L3b, L4):
  Input:  ~11,160 tok × $0.30/MTok = $0.0033
  Output: ~850 tok    × $2.50/MTok = $0.0021
  Think:  ~1,600 tok  × $2.50/MTok = $0.0040

ИТОГО гибрид: ~$0.013 (-61% vs текущая $0.033)
```

### 9.3. L2 двухшаговый (потенциал: -5-10% input)

По аналогии с L1 — shortlist групп, затем проверка примечаний для кандидатов. Особенно эффективно для тяжёлых разделов (VI, XI, XVI).

### 9.4. Context caching

Google Gemini API поддерживает context caching — system prompt + schema кэшируются, input оплачивается по сниженной ставке ($0.075/MTok для кэшированных).

### Сводка возможных оптимизаций

| # | Оптимизация | Текущая → после | Экономия | Нужен бенчмарк? |
|:-:|-------------|:---------------:|:--------:|:---------------:|
| 1 | thinkingBudget 1024→512 | $0.033 → $0.025 | -24% | Да |
| 2 | Гибрид flash-lite + flash | $0.033 → $0.013 | **-61%** | Да |
| 3 | L2 двухшаговый | -5-10% input | -2-3% | Нет |
| 4 | Context caching | -25% от cached tok | -5-8% | Нет |

## 11. Ключевые выводы

1. **gemini-2.5-flash стоит $0.30/$2.50 per MTok** — это дороже flash-lite ($0.25/$1.50), а не дешевле. Ранее указанные цены $0.075/$0.30 были ошибочными.

2. **Thinking tokens — 48% стоимости v8** ($0.016 из $0.033). Это фиксированный overhead ~$0.002 на каждый LLM-вызов, независимо от размера контекста.

3. **v8 стоит 2.2x дороже v6 за запрос** ($0.033 vs $0.015), но даёт +14 heading accuracy и +11 code-10.

4. **Стоимость за правильный heading: $0.035 (v8) vs $0.019 (v6)** = 1.8x дороже за качество. Но v8 не генерирует ложные needs_input (15% в v6), что частично компенсирует.

5. **L1 оптимизация сработала**: input упал с ~46K до ~35.5K (-23%). L1 уровень: с 16,630 до ~6,300 токенов (-62%).

6. **Главная точка оптимизации — thinking tokens**, не input. Варианты:
   - Уменьшить thinkingBudget (512 вместо 1024) → -24% стоимости
   - Гибрид flash-lite + flash только для L3b → **-61% стоимости** при сохранении thinking на критичном уровне

7. **gemini-2.5-flash-lite ($0.10/$0.40)** — перспективная альтернатива для некритичных уровней. Стоит протестировать.

```python

```

```

heavy  → L3a (shortlist), L3b (deep analysis)
```
