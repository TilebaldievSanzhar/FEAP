## 6. Возможности оптимизации токенов

### 6.1. L1: Селективная загрузка примечаний (-30% от общего input)

**Проблема**: L1 отправляет ВСЕ 52 примечания ко всем разделам (~13,890 токенов), хотя 12 из 21 разделов вообще не имеют примечаний.

**Решение**: Двухшаговый L1:
1. **L1a** — выбор 2-3 кандидатов разделов **без примечаний** (только имена = ~810 tok)
2. **L1b** — проверка примечаний **только для 2-3 кандидатов**

**Экономия**: ~13,000 токенов на L1 → от 46K до 33K на классификацию (**-28%**)

**Риск**: Дополнительный LLM-вызов (но дешёвый, ~1,500 tok).

### 6.2. L2: Загрузка примечаний только для кандидатов (-5-10%)

**Проблема**: L2 загружает примечания ко ВСЕМ группам раздела (до 14 групп × ~2,730 chars = ~12,700 tok для XI).

**Решение**: Аналогично L1 — сначала shortlist групп, потом проверка примечаний для кандидатов.

**Экономия**: ~3,000-8,000 токенов на L2 для тяжёлых разделов.

### 6.3. L3b: Ограничение пояснений (-3-5%)

**Проблема**: Пояснения к позициям могут быть очень длинными (до 52,997 chars = ~17,666 tok для одной позиции).

**Решение**: Обрезать пояснения до 2,000 chars на позицию (достаточно для ключевых включений/исключений).

**Экономия**: ~1,000-5,000 токенов для «тяжёлых» групп.

### 6.4. Кэширование system prompt (бесплатно при поддержке API)

**Суть**: System prompt одинаков для всех запросов одного уровня. Google Gemini API поддерживает context caching — можно кэшировать system prompt и схему.

**Экономия**: ~960-1,920 токенов system prompt + ~150-940 токенов схемы = до 2,860 tok на вызов.

### Сводка оптимизаций

| # | Оптимизация | Экономия tok | Экономия % | Сложность |
|:-:|-------------|:------------:|:----------:|:---------:|
| 1 | Селективные примечания L1 | ~13,000 | 28% | Средняя |
| 2 | Селективные примечания L2 | ~3,000-8,000 | 7-17% | Средняя |
| 3 | Обрезка пояснений L3b | ~1,000-5,000 | 2-11% | Простая |
| 4 | Context caching | ~2,000/вызов | varies | Простая |

С оптимизациями: **46K → ~20-27K токенов** на классификацию → стоимость падает до **$0.0020-0.0025**.

## 9. Ключевые выводы

1. **gemini-3.1-flash-lite-preview — неоптимальный выбор**: Preview-модель стоит $0.25/$1.50 за MTok — это **в 3.6x дороже** стабильного `gemini-2.5-flash` ($0.075/$0.30), который при этом мощнее. Переключение на 2.5-flash — первый шаг без каких-либо изменений кода.

2. **L1 потребляет 36% всех токенов** из-за загрузки ВСЕХ примечаний к разделам (~14K токенов). Селективная загрузка может сэкономить ~28% от общего input.

3. **Текущая стоимость $0.015 за классификацию**, при 100K = $1,510. После переключения на gemini-2.5-flash: $0.004 за классификацию, при 100K = $417.

4. **Гибридная стратегия** (gemini-2.5-flash для L0/L1/L2/L5 + Claude Haiku для L3b) — оптимальный баланс: ~$960/100K, потенциально значительный прирост качества на самом важном уровне.

5. **Оптимизация контекста может дополнительно сэкономить 40-60% токенов** без потери качества — селективная загрузка примечаний вместо «всё сразу».

6. **Output дешёвый** — всего ~2,400 токенов (5% от стоимости). Основной расход — input.

## Приложение: Конфигурация модели

```env
# Текущая конфигурация (.env)
LLM_PROVIDER=google
GEMINI_MODEL_LIGHT=gemini-3.1-flash-lite-preview    # L0, L1, L5
GEMINI_MODEL_MEDIUM=gemini-3.1-flash-lite-preview   # L2, L4
GEMINI_MODEL_HEAVY=gemini-3.1-flash-lite-preview    # L3a, L3b
```

**Все три tier-а используют одну и ту же модель** — дифференциация по сложности не работает.

### Маппинг tier → level

```
light  → L0 (enrichment), L1 (section), L5 (final code)
medium → L2 (group), L4 (subposition)
heavy  → L3a (shortlist), L3b (deep analysis)
```

### Max output tokens по уровням

```
L0: 2,048    L1: 2,048    L2: 2,048
L3: 4,096    L4: 2,048    L5: 1,024
```
