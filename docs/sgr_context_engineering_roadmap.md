# SGR + Context Engineering: анализ и направления оптимизации

**Дата:** 2026-03-23
**Контекст:** После v10b бенчмарка (heading=99%, code-10=74% скоррект.), внедрения per-level model selection и переключения L4 на Haiku 4.5

---

## 1. Текущее состояние

### 1.1 Распределение ошибок (v10b, скорректированный)

| Уровень ошибки | Кол-во | % от всех ошибок | Уровень каскада |
|:--|:--:|:--:|:--|
| subheading (6 цифр) | 14 | 54% | L4 |
| code_8 (8 цифр) | 7 | 27% | L5 |
| code_10 (10 цифр) | 2 | 8% | L5 |
| heading (4 цифры) | 1 | 4% | L3 |
| section | 2 | 8% | L1 (backtrack loop + сетевая) |

**Вывод:** L4 — главный bottleneck (54% ошибок). L5 — вторичный (35%). L1-L3 практически решены (heading=99%).

### 1.2 Что показал v10: SGR overhead для слабых моделей

В v10 были добавлены 5 SGR-полей в L4/L5 для flash-lite. Результат: **net-negative** (-3 pp code-10 vs v9).

| Метрика | v9 (без L4/L5 SGR) | v10b (с L4/L5 SGR) |
|:--|:--:|:--:|
| Code-10 | 77% | 74% |
| Улучшения | — | +2 (H20, H21) |
| Регрессии | — | -5 (M05, H15, H24, M25, E22) |

**Причина:** flash-lite имеет ограниченный «бюджет внимания». Каждое дополнительное SGR-поле отнимает генеративную способность от decision-полей (`selected_*`, `confidence`). Модель тратит токены на заполнение аналитических полей, но качество этого анализа недостаточно, чтобы улучшить финальный выбор.

### 1.3 Конфигурация моделей (с per-level selection)

| Уровень | Провайдер | Модель | SGR-полей | Статус |
|:--|:--|:--|:--:|:--|

| L1 section | Google | flash-lite | 4 (shortlist + verify) | Оптимально |

## 2. Архитектурные наблюдения

### 2.1 Shared template: tree_nodes.jinja2

**Факт:** `tree_nodes.jinja2` используется на ВСЕХ уровнях каскада (L1-L5) для рендеринга узлов дерева ТН ВЭД. В v10 изменение этого шаблона (добавление `{% if %}` для `parent_category`) вызвало лишние пустые строки через whitespace в Jinja2 → регрессия на ВСЕХ уровнях, включая 2 новые section-level ошибки.

**Проблема:** разным уровням нужны разные представления одних данных:
- L1: 21 раздел — просто `**XVI** — Машины, оборудование...`
- L2: 5-15 групп раздела — аналогично простой формат
- L4: 2-10 субпозиций с иерархическим контекстом, пороговыми значениями, `parent_category`

**Варианты решения:**

**A) Strict shared template** (текущий подход после отката)
- Shared template = только простой формат, без `{% if %}`
- Level-специфичная логика — в отдельных шаблонах
- Плюс: DRY, нет риска regression
- Минус: нет возможности адаптировать формат под уровень

**B) Per-level override с fallback**
- `tree_nodes.jinja2` — default
- `tree_nodes_l4.jinja2` — если существует, используется для L4 вместо default
- Плюс: гибкость, можно добавить `parent_category` только для L4
- Минус: больше файлов, нужна логика fallback в рендере

**Рекомендация:** Вариант B. Позволяет безопасно экспериментировать с форматом на конкретном уровне, не затрагивая остальные. Реализация: в context_builder проверять наличие `tree_nodes_l{level}.jinja2`, если нет — использовать `tree_nodes.jinja2`.

### 2.2 SGR fields должны соответствовать силе модели

Ключевой инсайт v10: **одинаковый набор SGR-полей не подходит для всех моделей**.

| Модель | Рекомендуемый SGR budget | Обоснование |
|:--|:--:|:--|
| flash-lite | 2-3 поля | Ограниченный бюджет внимания, каждое лишнее поле — минус для decision |
| Haiku 4.5 | 4-6 полей | Может утилизировать аналитические поля, достаточно мощная |
| Sonnet / 2.5-flash | 5-8 полей | Полный SGR Cascade, включая consistency checks |
| Opus / Pro | 3-4 поля | Модель достаточно умна сама; SGR скорее scaffolding, не костыль |

**Следствие:** с per-level model selection можно иметь per-level SGR complexity:
- L4 на Haiku → полный набор SGR (hierarchy_parsing, threshold_analysis, consistency_check)
- L5 на flash-lite → минимальный SGR (relevant_parameters, threshold_comparison)

Это можно реализовать двумя способами:
1. **Разные Pydantic-схемы** по модели (сложно, хрупко)
2. **Одна схема, но промпт направляет** — поля с `default=""` заполняются настолько глубоко, насколько модель способна. Промпт для flash-lite говорит «заполни кратко», для Haiku — «заполни развёрнуто с цитатами».

Рекомендация: вариант 2 (промпт-driven SGR depth).

## 3. Нереализованный потенциал

### 3.1 Синхронизация контекста с SGR-полями

**Текущее:** SGR-поля в схеме и контекст в user-message слабо связаны.

```
SGR field order:          Context order (user message):
1. parameter_extraction   [Карточка товара]
2. threshold_analysis     [Цепочка решений]
3. candidates             [Список субпозиций]     ← позиции далеко от SGR step 2
4. selected_*             [Примечания]
                          [Пояснения]
                          [ОПИ]
```

**Проблема:** когда модель заполняет `threshold_analysis`, ей нужно найти пороги в текстах субпозиций. Но субпозиции — это один блок текста, а пороги разбросаны по разным формулировкам («массой не более 250 г», «мощностью свыше 1 кВт»).

**Предложение — context mirroring:**

```
SGR field: parameter_extraction
  ↕ context block: ПАРАМЕТРЫ ТОВАРА (извлечённые из карточки)
    масса: 720 г
    мощность: не указана
    назначение: бытовой

SGR field: threshold_analysis
  ↕ context block: СУБПОЗИЦИИ С ВЫДЕЛЕННЫМИ ПОРОГАМИ
    842211 — бытовые  [порог: нет числового]
    842219 — прочие   [порог: нет числового]
    842290 — части    [тип: ЧАСТИ, не целое!]
```

Когда порядок и структура контекста **зеркалят** порядок SGR-полей, модель тратит меньше внимания на поиск информации. Это чистый context engineering — бесплатно по стоимости модели.

**Сложность реализации:** средняя. Нужно изменить context-шаблоны для L4/L5, чтобы они выделяли пороги и аннотировали тип субпозиции.

### 3.2 Аннотированные узлы дерева для L4

**Текущий формат:**
```
- **842211** — Бытовые
- **842219** — Прочие
- **842290** — Части
```

**Предлагаемый формат (для L4):**
```
[1/3] 842211 — Бытовые                    ← КОНКРЕТНАЯ субпозиция
[2/3] 842219 — Прочие                     ← ОСТАТОЧНАЯ (выбирай только если ничего конкретного)
[3/3] 842290 — Части                      ← ЧАСТИ (не выбирай если товар — целое устройство!)
```

Аннотации выполняют функцию SGR, но в контексте, а не в схеме:
- `КОНКРЕТНАЯ` — направляет внимание на первый приоритет (ОПИ 3а)
- `ОСТАТОЧНАЯ` — предупреждает о ловушке «прочие» (самая частая ошибка L4)
- `ЧАСТИ` — предупреждает о ловушке «части vs целое» (паттерн P2 из v7)

**Сложность реализации:** низкая. Аннотации можно генерировать эвристически:
- Код заканчивается на `90`/`99` → `ОСТАТОЧНАЯ`
- Текст содержит «части», «принадлежности» → `ЧАСТИ`
- Иначе → `КОНКРЕТНАЯ`

Это не требует LLM и может дать значительный эффект, особенно для flash-lite.

### 3.3 «Негативные» SGR-поля

**Текущее:** SGR направляет к решению — `selected_*` в конце. Но не заставляет модель **отвергнуть** альтернативы.

**Предложение:** добавить поле `rejected_with_reason` перед `selected_*`:

```python
class SubpositionResult(BaseModel):
    # ... SGR analytical fields ...
    candidates: list[SubpositionCandidate]
    rejected_with_reason: str   # "842290 отвергнута: товар — целое устройство, не часть"
    selected_subposition: str   # заполняется ПОСЛЕ явного отвержения
```

**Зачем:** заставляет модель явно сформулировать, почему **не выбрала** ближайшего конкурента. Это cognitive forcing function — если модель не может сформулировать причину отвержения, значит выбор неуверенный.

**Ограничение:** +1 SGR-поле = +overhead. Подходит для Haiku/Sonnet, не для flash-lite.

### 3.4 Few-shot examples в промптах

**Текущее:** промпты содержат инструкции, но не примеры.

**Предложение:** для L4 (самый проблемный уровень) добавить 1-2 few-shot примера в system prompt:

```
ПРИМЕР:
Товар: «Посудомоечная машина бытовая, встраиваемая»
Субпозиции: 842211 (бытовые), 842219 (прочие), 842290 (части)
Анализ: товар — целое бытовое устройство → 842211 (конкретная), НЕ 842290 (части)
Результат: 842211
```

Это занимает ~50-100 токенов input, но даёт модели **образец правильного рассуждения**.

**Ограничение:** примеры нужно подбирать так, чтобы они покрывали типичные ошибки (выбор «прочие», путаница «части/целое»), но не создавали bias для конкретных товаров.

## 4. Приоритизация

| # | Действие | Сложность | Ожидаемый эффект | Зависимости |
|:-:|:--|:--:|:--:|:--|
| 1 | L4 на Haiku 4.5 | ✅ Сделано | Высокий | Per-level model selection |
| 2 | Аннотированные узлы для L4 (КОНКРЕТНАЯ/ОСТАТОЧНАЯ/ЧАСТИ) | Низкая | Средний-Высокий | Per-level tree_nodes template |
| 3 | Context mirroring (порядок контекста = порядок SGR) | Средняя | Средний | Изменение context templates |
| 4 | Промпт-driven SGR depth (кратко для lite, развёрнуто для Haiku) | Низкая | Средний | — |
| 5 | `rejected_with_reason` SGR-поле для L4 | Низкая | Средний | Только для Haiku+ |
| 6 | Few-shot examples в L4 промпте | Низкая | Средний | Нужно подобрать примеры |
| 7 | Per-level tree_nodes override (tree_nodes_l4.jinja2) | Средняя | Enabler для #2 | Изменение context_builder |

### Рекомендуемый порядок

**Фаза 1** (текущая): Бенчмарк L4 на Haiku (#1) → измерить baseline эффекта от смены модели.

**Фаза 2** (context engineering): #7 → #2 → бенчмарк. Аннотации узлов — дешёвое и потенциально самое эффективное изменение. Если «прочие»-ошибки уменьшатся, это подтверждение подхода.

**Фаза 3** (SGR tuning): #4 + #5 → бенчмарк. Усилить SGR для Haiku, где модель может использовать аналитические поля по назначению.

**Фаза 4** (advanced): #3 + #6 → бенчмарк. Context mirroring и few-shot — более глубокие оптимизации.

## 5. Метрики успеха

| Метрика | v9 baseline | Цель после Фазы 1 | Цель после Фазы 2-3 |
|:--|:--:|:--:|:--:|
| Heading accuracy | 99% | 99% | 99% |
| Subheading accuracy | 84% | 87%+ | 90%+ |
| Code-10 accuracy | 77% | 80%+ | 85%+ |
| L4 error rate | 15% | 10%- | 7%- |
| Cost per classification | ~$0.004 | ~$0.006 | ~$0.007 |

Увеличение стоимости обусловлено переключением L4 на Haiku ($0.80/$4.00 input/output vs $0.075/$0.30 flash-lite). Один вызов L4 на Haiku ≈ $0.002-0.004 vs $0.0003 на flash-lite. Это +$0.002-0.004 на классификацию — приемлемо при значительном росте accuracy.

## 6. Принцип: «дешёвый контекст, дорогая модель только где нужно»

Общая стратегия оптимизации:

1. **Context engineering** (бесплатно) — формат, порядок, аннотации в user-message
2. **SGR fields** (дёшево, ~150-300 output токенов) — направление рассуждений через структуру схемы
3. **Stronger model** (дорого) — только для уровней, где #1 и #2 недостаточны

L4 — единственный уровень, где пункт #3 оправдан данными. Все остальные уровни могут быть улучшены через #1 и #2.
