# Системная проблема: наименования узлов дерева ТН ВЭД

## Краткое описание

Каскадный классификатор на каждом уровне показывает LLM список вариантов для выбора — например, на уровне L4 (субпозиция) показывает список 6-значных кодов с их названиями. LLM читает эти названия и на их основе делает выбор.

**Проблема:** у значительной части узлов дерева (субпозиций, позиций) названия либо **одинаковые** для разных кодов, либо **пустые**. В результате LLM получает список вида:

```
940340: Мебель; постельные принадлежности, матрацы...
940350: Мебель; постельные принадлежности, матрацы...
940360: Мебель; постельные принадлежности, матрацы...
```

...и не может различить субпозиции, потому что все три имеют идентичный текст. Это как если бы вам дали меню в ресторане, где все блюда называются «еда» — вы не сможете выбрать.

---

## Откуда берётся проблема

### Источник данных

Данные ТН ВЭД загружаются из Excel-файла с сайта tws.by. Каждая строка — это один 10-значный код (лист дерева). Наименование записано в одну ячейку через разделитель `🠺` (стрелка):

```
0409000000 | Мёд натуральный
1001990000 | зерно прочее 🠺 прочая
9403401000 | Разные промышленные товары (гр. 94-96) 🠺 Мебель; постельные принадлежности... 🠺 Мебель прочая и ее части 🠺 мебель деревянная типа кухонной 🠺 мебель кухонная секционная
9403609009 | Разные промышленные товары (гр. 94-96) 🠺 Мебель; постельные принадлежности... 🠺 Мебель прочая и ее части 🠺 мебель деревянная прочая 🠺 мебель деревянная прочая 🠺 прочая
```

Стрелка `🠺` разделяет уровни иерархии, но:

1. **Количество уровней непостоянно** — от 1 до 11 частей у разных кодов
2. **Нет стандартной привязки** — часть [0] может быть разделом, группой, позицией или сразу субпозицией
3. **У одной позиции** разные листья могут иметь **разное количество частей**

### Почему это создаёт проблему

Дерево ТН ВЭД имеет 5 жёстких уровней: Раздел → Группа → Позиция → Субпозиция → Лист. Но текстовая иерархия в Excel **не совпадает** с этими уровнями. Парсер `build_tree.py` должен «вывести» имя каждого промежуточного узла из текстов его дочерних листьев.

### Конкретный пример: позиция 9403 (мебель)

В Excel у листов позиции 9403 разная глубина `name_parts`:

**Лист 9403105100** (субпозиция 940310, мебель металлическая для офисов):
```
parts[0]: "не превышающая по высоте 80 см"
parts[1]: "столы письменные"
```
Всего **2 части**. parts[0] — это описание субпозиции, parts[1] — описание листа.

**Лист 9403401000** (субпозиция 940340, мебель деревянная кухонная):
```
parts[0]: "Разные промышленные товары (гр. 94-96)"
parts[1]: "Мебель; постельные принадлежности, матрацы..."
parts[2]: "Мебель прочая и ее части"
parts[3]: "мебель деревянная типа кухонной"
parts[4]: "мебель кухонная секционная"
```
Всего **5 частей**. Только parts[3] — это описание субпозиции.

Если парсер пытается взять имя субпозиции по **фиксированному индексу** (например, parts[1]), то:
- Для 940310: parts[1] = "столы письменные" — это имя **листа**, не субпозиции
- Для 940340: parts[1] = "Мебель; постельные принадлежности..." — это имя **группы** 94

Ни в одном случае фиксированный индекс не даёт правильный ответ.

## Как было (старый алгоритм)

**Файл:** `scripts/build_tree.py`, функция `infer_parent_name()`

Старый подход: для каждого уровня иерархии использовался **фиксированный индекс** в массиве `name_parts`:

- Группы (level 1): `infer_parent_name(leaves, 0)` — брал parts[0]
- Позиции (level 2): `infer_parent_name(leaves, 0)` — тоже parts[0]
- Субпозиции (level 3): `infer_parent_name(leaves, 1)` — брал parts[1]

`infer_parent_name` находил **самое частое значение** по указанному индексу среди всех листьев узла.

### Результат

Для позиции 9403 все субпозиции (940310–940399) получали одно и то же имя: текст заголовка группы 94 — «Мебель; постельные принадлежности, матрацы...», потому что у большинства листьев parts[1] содержит именно это.

**Масштаб проблемы:**
- **68% субпозиций** (3822 из 5612) имели неуникальные имена в рамках своей позиции
- LLM на уровне L4 получала список из 3–10 субпозиций с одинаковым текстом и классифицировала **наугад**

## Что было сделано (новый алгоритм)

**Файл:** `scripts/build_tree.py`, новые функции `_lcp()` и `_infer_name_by_lcp()`

### Идея

Вместо фиксированного индекса используем **динамический анализ** — сравниваем тексты листьев субпозиции с текстами листьев соседних (sibling) субпозиций и находим часть, которая **уникальна** именно для этой субпозиции.

### Алгоритм по шагам

**Шаг 1. LCP внутри субпозиции**

Для каждой субпозиции берём `name_parts` всех её листьев и находим **самый длинный общий префикс** (Longest Common Prefix, LCP). Это части текста, которые **общие для всех листьев** этой субпозиции — значит, они описывают субпозицию или что-то выше.

Пример для субпозиции 940340:
```
Лист 9403401000: ["Разные промышленные...", "Мебель;...", "Мебель прочая...", "мебель деревянная типа кухонной", "мебель кухонная секционная"]
Лист 9403409000: ["Разные промышленные...", "Мебель;...", "Мебель прочая...", "мебель деревянная типа кухонной", "прочая"]

LCP = ["Разные промышленные...", "Мебель;...", "Мебель прочая...", "мебель деревянная типа кухонной"]
```

Для субпозиции 940360:
```
LCP = ["Разные промышленные...", "Мебель;...", "Мебель прочая...", "мебель деревянная прочая"]
```

**Шаг 2. Убрать «шум» — общий с сиблингами**

LCP содержит не только имя субпозиции, но и имена вышестоящих уровней (группа, позиция). Чтобы найти именно **субпозиционную** часть, сравниваем LCP текущей субпозиции с LCP каждого соседа и находим **максимальную длину общего начала**.

Сравнение 940340 и 940360:
```
940340 LCP: ["Разные промышленные...", "Мебель;...", "Мебель прочая...", "мебель деревянная типа кухонной"]
940360 LCP: ["Разные промышленные...", "Мебель;...", "Мебель прочая...", "мебель деревянная прочая"]

Совпадают первые 3 элемента → max_shared = 3
```

**Шаг 3. Имя = части после общего**

```
940340 specific = LCP[3:] = ["мебель деревянная типа кухонной"] → "мебель деревянная типа кухонной"
940360 specific = LCP[3:] = ["мебель деревянная прочая"]        → "мебель деревянная прочая"
```

| 940340 | Мебель; постельные принадлежности... | **мебель деревянная типа кухонной** |
| 940350 | Мебель; постельные принадлежности... | **мебель деревянная типа спальной** |

## Какие проблемы остались

Несмотря на значительное улучшение, **17.1% позиций** (164 из 957) по-прежнему имеют субпозиции с дублирующимися именами. Причины:

### 1. Субпозиции с именем «прочие» / «прочая»

Самый частый случай. В ТН ВЭД многие субпозиции буквально называются «прочие» — это catch-all категории. Если в позиции две таких субпозиции (например, 010129 «прочие» и 010190 «прочие»), алгоритм не может их различить, потому что в Excel они действительно называются одинаково.

**Пример — позиция 0101 (лошади):**
```
010121: "чистопородные племенные животные"
010129: "прочие"        ← дубликат
010130: "ослы"
010190: "прочие"        ← дубликат
```

В реальной номенклатуре 010129 — это «лошади прочие», а 010190 — это «мулы и лошаки». Но Excel не содержит этого контекста — обе строки просто говорят «прочие».

**Масштаб:** ~100 позиций имеют 2+ субпозиции с именем «прочие» или «прочая» (сократилось с ~200 благодаря ФНС, где часть «прочих» получила уточнённые имена).

### 2. Пустые имена

Когда у субпозиции всего один лист, и LCP этого листа полностью совпадает с LCP сиблингов, специфическая часть оказывается пустой.

**Пример — позиция 0203 (свинина):**
```
020311: ""     ← пусто
020312: ""     ← пусто
020319: ""     ← пусто
020321: ""     ← пусто
020322: ""     ← пусто
020329: ""     ← пусто
```

Все листы этой позиции имеют `name_parts` длиной 1–2, и единственная часть описывает сам лист, а не субпозицию. В Excel просто нет информации о том, как называется субпозиция.

### 3. Непоследовательная глубина путей

Внутри одной позиции одни субпозиции имеют листы с 2 частями, другие — с 6 частями. Из-за этого LCP всей позиции пустой (нет общего начала), и алгоритм не может определить, где кончается «позиционный шум» и начинается имя субпозиции.

**Пример — позиция 9403:**
- 940310 листы: 2–3 части, начинаются с «не превышающая по высоте 80 см»
- 940340 листы: 5 частей, начинаются с «Разные промышленные товары...»

Наш алгоритм корректно обрабатывает 940340 (находит пересечение с 940360), но для 940310 нет сиблинга с таким же длинным путём, и имя «не превышающая по высоте 80 см» хоть и уникальное, но не очень осмысленное.

## Реализованное решение: справочник ФНС + комбинированный алгоритм

### Источник данных

**ФНС России (nalog.gov.ru)** публикует бесплатный справочник TNVED.ZIP с официальными наименованиями:

**URL:** `https://www.nalog.gov.ru/html/sites/www.new.nalog.ru/docs/sprav/tnved/TNVED.ZIP`

| Файл | Уровень | Записей | Содержит |
|------|---------|---------|----------|
| TNVED1.TXT | Разделы (I–XXI) | 22 | Название + полный текст примечаний |
| TNVED2.Txt | Группы (01–97) | 97 | Собственное наименование + примечания |
| TNVED3.Txt | Позиции (4 цифры) | 957 | Собственное наименование |
| TNVED4.Txt | Субпозиции (6+ цифр) | 5612 | Листья с дефисной иерархией |

Формат: pipe-delimited TXT, кодировка CP866, версионированные записи (valid_from/valid_to).

### Как реализовано

**Новый скрипт:** `scripts/parse_fns_reference.py`
- Парсит все 4 файла
- Фильтрует текущие записи (valid_to пустой)
- Для субпозиций из TNVED4: берёт запись с минимальным dash-level для каждого 6-значного кода
- Сохраняет в `data/reference/fns_names.json`

**Обновлённый `scripts/build_tree.py`:**
- **Группы:** имя из ФНС (всегда)
- **Позиции:** имя из ФНС (всегда) — например, «НАСОСЫ ЖИДКОСТНЫЕ С РАСХОДОМЕРАМИ ИЛИ БЕЗ НИХ; ПОДЪЕМНИКИ ЖИДКОСТЕЙ» вместо выведенного «Насосы жидкостные с расходомерами...»
- **Субпозиции:** комбинированный алгоритм:
  1. Если ФНС-имя уникально среди сиблингов → используем ФНС
  2. Если ФНС даёт дубликат → используем LCP
  3. Если LCP тоже даёт дубликат → комбинируем: `"FNS_name (LCP_name)"`

### Результат

| Метрика | Старый алгоритм | LCP (v2) | **FNS+LCP (v3)** |
|---------|----------------|----------|-------------------|
| Позиции с уникальными именами субпозиций | 29.3% | 74.3% | **82.9%** |
| Дубликатов осталось | 70.7% | 25.7% | **17.1%** |

### Примеры улучшений (FNS vs LCP)

**Позиция 8413 (насосы):**
| Субпозиция | LCP (v2) | FNS (v3) |
|-----------|----------|----------|
| 841370 | *Реакторы ядерные, котлы...* (текст группы) | **насосы герметичные центробежные для нагревательных систем** |
| 841382 | подъемники жидкостей | **станки-качалки** |

**Позиция 0101 (лошади):**
| Субпозиция | LCP (v2) | FNS (v3) |
|-----------|----------|----------|
| 010129 | прочие | **убойные** |
| 010190 | прочие | **прочие** (остался дубликат — но 010129 теперь отличается) |

## Какие проблемы остались (17.1% дубликатов)

### Точные цифры

| Метрика | Значение |
|---------|----------|
| Субпозиций с дубликатами имён (среди сиблингов) | **869** из 5,612 (15.5%) |
| Позиций с хотя бы одним дубликатом | **164** из 1,228 (13.4%) |
| Всего «групп дубликатов» (наборы одноимённых сиблингов) | 339 |

### Категоризация 339 групп дубликатов

| Категория | Групп | Описание |
|-----------|-------|----------|
| A. Точные «прочие» | 72 | Имя = "прочие"/"прочая"/"прочее"/"прочий" |
| B. «Прочие» с контекстом | 30 | Содержит «прочие» + квалификатор, но всё равно дублируется |
| C. Ссылки на дополнительные примечания | 6 | Длинные тексты вида "в порядке, указанном в доп. примечании…" |
| **D. Параллельная структура (основная масса)** | **227** | Одинаковое свойство для разных видов/состояний |
| E. Баг кросс-проверки FNS↔LCP | 8 | ФНС даёт уникальное имя, но LCP его перезаписывает (см. ниже) |

**97.6% проблемы — в самих данных ФНС/TWS** (категории A–D), а не в коде парсера.

### Корневая причина: «виртуальные» промежуточные узлы

Номенклатура ТН ВЭД между позицией (4 цифры) и субпозицией (6 цифр) содержит **неявные промежуточные группировки**, обозначенные дефисами в официальном тексте, но не имеющие собственных кодов:

```
0802 ПРОЧИЕ ОРЕХИ
├── [виртуальный: миндаль]              ← 1-dash, нет кода
│   ├── 080211  "в скорлупе"            ← 2-dash
│   └── 080212  "очищенный"             ← 2-dash
├── [виртуальный: лещина]               ← 1-dash, нет кода
│   ├── 080221  "в скорлупе"            ← дубликат!
│   └── 080222  "очищенный"             ← дубликат!
├── [виртуальный: грецкие]              ← 1-dash, нет кода
│   ├── 080231  "в скорлупе"            ← дубликат!
│   └── 080232  "очищенные"             ← дубликат!
```

Имя субпозиции ("в скорлупе") одинаково, потому что различающий контекст ("миндаль" vs "лещина") живёт на виртуальном уровне, которого **нет ни в ФНС-файлах, ни в TWS Excel** как отдельной записи.

#### Худший случай: позиция 6108 (женское нижнее бельё)

11 субпозиций используют всего 3 имени:

| Субпозиция | Имя в дереве | Виртуальный родитель (1-dash) |
|-----------|--------------|-------------------------------|
| 610811 | из химических нитей | комбинации и нижние юбки |
| 610819 | из прочих текстильных материалов | комбинации и нижние юбки |
| 610821 | из хлопчатобумажной пряжи | **трусы и панталоны** |
| 610822 | из химических нитей | **трусы и панталоны** |
| 610829 | из прочих текстильных материалов | **трусы и панталоны** |
| 610831 | из хлопчатобумажной пряжи | **ночные сорочки и пижамы** |
| 610832 | из химических нитей | **ночные сорочки и пижамы** |
| 610839 | из прочих текстильных материалов | **ночные сорочки и пижамы** |
| 610891 | из хлопчатобумажной пряжи | прочие |
| 610892 | из химических нитей | прочие |
| 610899 | из прочих текстильных материалов | прочие |

Без 1-dash контекста LLM получает список из 11 пунктов, где 4 называются "из химических нитей" — выбор невозможен.

#### Другие характерные примеры

- **0304 (рыбное филе):** 7 виртуальных группировок (свежая тилапия, мороженая тилапия…); "тилапии" дублируется для 030431 и 030461
- **0802 (орехи):** "в скорлупе" дублируется 5 раз для разных видов орехов
- **0908 (пряности):** "недробленый и немолотый" — для мускатного ореха, мациса, кардамона
- **0203 (свинина):** 6 субпозиций, все с пустыми именами — различие "свежая/охлаждённая" vs "замороженная"

### Баг кросс-проверки FNS↔LCP (категория E)

В `build_tree.py` строки 312–318 при проверке уникальности LCP-имени оно сравнивается **только с LCP-именами** других сиблингов. Но **не проверяется**, что LCP-имя не совпадает с FNS-именем какого-то сиблинга, которое уже было назначено.

**Пример — позиция 4403 (древесина):**

| Субпозиция | FNS-имя | FNS уникально? | Итоговое имя | Способ |
|-----------|---------|----------------|--------------|--------|
| 440322 | "сосна обыкновенная вида Pinus sylvestris L." | ✅ Да | "сосна обыкновенная..." | FNS |
| 440321 | "бревна" | ❌ Нет (есть у 440323, 440325…) | "сосна обыкновенная..." | LCP ← **коллизия!** |

LCP вычислил для 440321 имя "сосна обыкновенная вида Pinus sylvestris L.", проверил уникальность среди LCP-имён сиблингов — уникально. Но не проверил, что у сиблинга 440322 это имя уже занято через FNS.

**Все 8 случаев багов:**

| Позиция | Субпозиция (баг) | Коллидирует с | Итоговое дублирующееся имя |
|---------|-----------------|---------------|---------------------------|
| 0305 | 030539 | 030532 | "прочее" |
| 3822 | 382219 | 382290 | "прочие" |
| 4403 | 440321 | 440322 | "сосна обыкновенная вида..." |
| 4403 | 440323 | 440324 | "ель обыкновенная вида..." |
| 5407 | 540769 | 540720 | "прочие" |
| 6402 | 640299 | 640219 | "прочая" |
| 8418 | 841810 | 841821 | "емкостью более 340 л" |
| 8462 | 846242 | 846249 | "пробивные или вырубные..." |

**Исправление:** добавить кросс-проверку — перед назначением LCP-имени проверять, что оно не совпадает ни с одним FNS-именем, которое уже будет использовано как финальное у сиблинга.

### Где хранятся виртуальные родители

Информация о 1-dash виртуальных узлах существует в двух источниках:

1. **TNVED4.TXT** (`data/reference/tnved_fns/`) — каждый лист имеет dash-level, который указывает глубину в поддереве позиции. Dash-level 2 означает, что над ним есть виртуальный 1-dash родитель. Но текст этого родителя **не записан отдельной строкой** — он закодирован только как общая часть пути в TWS Excel.

2. **TWS Excel** (`data/TWS_TNVED_2026-02-17.xlsx`) — стрелочная иерархия `name_parts` содержит промежуточные уровни. Для ~53% проблемных случаев предпоследний сегмент пути содержит имя виртуального родителя. Для ~47% (158 групп) TWS-путь тоже не различает сиблингов.

3. **Официальный PDF номенклатуры ЕЭК** — содержит полную дефисную иерархию с текстами всех промежуточных узлов. PDF машиночитаемый (не сканированный). Это «золотой стандарт», но в проекте его пока нет.

## Влияние на качество классификации

### Benchmark-результаты

| Прогон | Heading accuracy | Code-10 accuracy | Completion rate |
|--------|-----------------|------------------|-----------------|
| v1 (старые имена, баг L4) | 72.0% | 52.0% | 72.0% |
| v2 (LCP-имена, фикс L4) | 84.0% | 60.0% | 84.0% |
| **v3 (FNS+LCP, фикс L4)** | **84.0%** | **68.0%** | **84.0%** |

Общий прирост от v1 к v3: heading +12 п.п., code-10 **+16 п.п.**, completion +12 п.п.

Из прироста code-10 (+16 п.п.):
- +8 п.п. — от фикса бага с пустым candidates (3 кейса: мёд, гвозди, велосипед)
- +4 п.п. — от LCP-алгоритма (1 кейс: сыр SMOKE-H02 теперь проходит)
- +4 п.п. — от ФНС-справочника (1 кейс: труба M07 — точный 10-значный код, + набор пикника H01 — устранена регрессия v2)

### Где именно имена влияют

1. **L4 (субпозиция)** — основной уровень, где LLM выбирает из списка. Именно здесь одинаковые имена критичны. Пример: стол (E08) — LLM выбрала 940360 вместо 940340.

2. **L3 (позиция)** — аналогичная проблема для позиций внутри группы, но менее критичная, так как LLM также использует пояснения и примечания.

3. **L5 (лист)** — листы имеют собственные имена из Excel, проблема не затрагивает.

### Оценка «потолка»

Даже с идеальными именами, code-10 accuracy не станет 100% — остаются проблемы с:
- Числовыми порогами (водопоглощение, диаметр, мощность)
- Отсутствующими пояснениями (explanatory notes не загружены)
- Калибровкой confidence

Но heading accuracy может достичь **95%+** при полном устранении проблемы наименований.

### Пути решения оставшихся дубликатов

| Вариант | Статус | Покрытие | Сложность |
|---------|--------|----------|-----------|
| 1. Справочник ФНС | **Реализован** (v3) | — | — |
| 2. Контекст из дочерних листьев (LCP) | **Реализован** (v2) | — | — |
| **3. Фикс бага FNS↔LCP кросс-проверки** | **Не реализован** | 8 групп / 16 субпозиций | Низкая |
| **4. Виртуальные родители из TNVED4 dash-level + TWS name_parts** | **Не реализован** | ~181 из 339 групп (53%) | Средняя |
| **5. Парсинг полной дефисной иерархии из PDF номенклатуры ЕЭК** | **Не реализован** | До 100% (все 339 групп) | Средняя |
| 6. Обогатить из пояснений (explanatory notes) | Не реализован | Часть «прочие» | Высокая |

**Рекомендация: переход на PDF ЕЭК как единственный источник дерева и имён (v4)**

Гибридный подход (TWS + ФНС + LCP) архитектурно хрупкий: 3 неполных источника, 2 кастомных алгоритма, баги на стыках, и всё равно 17% дубликатов. При каждом обновлении номенклатуры нужно синхронизировать все 3 источника.

Вместо этого — **один авторитетный источник**: PDF номенклатуры ЕЭК, который содержит **полную дефисную иерархию** со всеми виртуальными узлами. TWS Excel остаётся только для ставок пошлин и единиц измерения.

## Результаты исследования: парсинг PDF ЕЭК (17 марта 2026)

### Источник данных

**URL:** https://eec.eaeunion.org/comission/department/catr/ett/

На странице — **96 PDF-файлов** (по одному на группу 01–97, группа 77 не существует). Каждый файл содержит:
- Примечания к разделу (если первая группа раздела)
- Примечания к группе
- Полную таблицу кодов с дефисной иерархией
- Ставки пошлин и единицы измерения

Файлы обновляются ЕЭК при изменении номенклатуры. Актуальная версия — от 08.03.2026 для большинства групп.

### Формат PDF

- Создан в Microsoft Word → PDF 1.5
- **Машиночитаемый** (не сканированный)
- Шрифты: Times New Roman (WinAnsiEncoding + Identity-H)
- Текст извлекается через PyMuPDF (fitz) с `PYTHONUTF8=1`
- Кириллица корректна (Unicode codepoints U+0400–U+04FF)

### Структура содержимого

Каждый PDF — табличный документ с колонками: Код ТН ВЭД | Наименование | Доп. ед. изм. | Ставка пошлины.

В колонке «Наименование» — дефисная иерархия через символ en-dash (`–`, U+2013):

```
0802  Прочие орехи...                        ← позиция (4 цифры)
      – миндаль:                              ← виртуальный L1 (без кода!)
0802 11   – – в скорлупе:                     ← субпозиция (6 цифр) + h6 header
0802 11 100 0  – – – горький                  ← лист (10 цифр)
0802 11 900 0  – – – прочий                   ← лист
0802 12   – – очищенный от скорлупы:          ← субпозиция
      – орех лесной, или лещина (Corylus spp.): ← виртуальный L1 (без кода!)
0802 21 000 0  – – в скорлупе                 ← лист (код совпадает с субпозицией)
```

Ключевое: **виртуальные узлы** (строки с дефисами, но без кода) — это именно те промежуточные группировки, которые отсутствуют в TNVED4 и TWS, но нужны для различения субпозиций.

        }

TWS Excel (1 файл)
  │
  ├── scripts/parse_excel.py           — извлечение ставок
  │       Извлекает: код 10, ставка, НДС, ед. измерения

### Обновление номенклатуры (ежегодное)

1. Скачать новые PDF с ЕЭК → `scripts/download_ett_pdfs.py`
2. Запустить парсер → `scripts/parse_ett_nomenclature.py`
3. Обновить Excel с tws.by (если изменились ставки)
4. Перестроить дерево → `scripts/build_tree.py`
5. Перезагрузить БД → `scripts/seed_db.py`

Один источник для имён → один парсер → нет рассинхронизации.
